### R5 pool proof (STATIC, compiled def-use)

Decoded from the verified ROM rather than asserted as a literal, and entered as a **double-entry
cross-check**: the generator records the pooled value it decoded, and the test independently
re-decodes the instruction and the pool word from the same verified bytes. Both must agree, so a
decoder bug on either side shows up as a mismatch. This is *not* an independent re-derivation —
both entries read the same ROM through the same Thumb LDR-literal rule, so this proves the decode
is stable and correctly placed, not that the rule is right. The rule itself rests on
`pin_gen3_site.instruction_offsets`, which is common to both sides.

| Function | `ldr` at | Pool slot | Pool value |
|---|---|---|---|
| `Task_DepositMenu` | `+0x8` -> `ldr r5,[pc,#0x21C]` | `+0x228` | `020324CC` (`&sStorage`) |
| `Task_ReleaseMon` | `+0x8` -> `ldr r5,[pc,#0x2E8]` | `+0x2F4` | `020324CC` (`&sStorage`) |

This is **static register reasoning over verified bytes**. It proves the compiled value. It does
**not** prove R5 is still live at `pc_deposit` `+0x16E` or `pc_release*` — that is the PHYSICAL
run's question and is carried as `runtime_liveness: OPEN_PHYSICAL` in the pack. Do not read the
`COMPILED_DEF_USE` evidence tag as liveness.

### Snapshot provenance (contract only, no consumer)

`pc_release_begin` / `pc_release` / `pc_deposit` carry a `snapshot` block describing the one-shot
pairing: the begin latch is consumed once by the next `pc_release` **from the same
`Task_ReleaseMon` invocation**, and is cleared on release, cancel, task change or storage reset. A
moved-mon flag clear emits no begin and must not reuse an older latch. `pc_deposit` must read
`sIsMonBeingMoved` before the storage call to tell a moved-mon release-clear from an acquisition
deposit.

This is metadata for a future run card. **No runtime consumer is added or implied**, and the
admission gate still refuses `gen3_exp`. The existing consumers (`upr_pipeline.py:348-362`,
`e2e_duo.py:3106`) read only `address`/`expected_hex`/`rom_offset`/`capture_offset`/`point`/
`mode`/`function`/`symbol`, all of which are unchanged, so the addition is inert to them.

### What the static checks prove, and what they do not

`test_pc_cursor_globals_are_sym_bound_with_consistent_offsets` proves symbol uniqueness and
address layout. `test_r5_pool_resolves_to_sstorage_by_decoding_not_by_literal` proves the pooled
constant. `test_release_snapshot_latch_is_a_contract_with_no_consumer` proves the contract text
and that no cursor is referenced that the generator did not bind. None of these is a runtime
observation, and the test names say so deliberately.

**Unreachable negative, recorded honestly:** a "drifted pool word is rejected" negative cannot be
written, because mutating the ROM trips the SHA-1 identity gate in `expansion_inputs` before any
pool byte is decoded. The control asserts that ordering (`identity mismatch`) instead of faking a
pool-drift rejection.

## 2026-10-01 update

**Release pairing is frame-window, not SP+4.** `pc_release_begin` (`Task_ReleaseMon+0xFA`) and
`pc_release` (`+0x17C`) are two sites inside **one function body**; the only SP changes are that
function's prologue and epilogue, so SP is *equal* at both and the vanilla SP+4 token can never
fire. The pack therefore declares, per site,
`pairing: {mode: "frame_window", window: 0, reason: …}` (`tools/gen_gen3_engine_signals.py:1515`
`EXPANSION_PAIRING`, emitted at `:1638-1639`). The client reads it at
`lua/gen3/client.lua:1315-1319`: a declared `frame_window` pairs only when both fire on the same
frame; **a declared-but-unknown mode is refused rather than falling back to the SP rule**
(`02df12c6`); a pack with no `pairing` key keeps the vanilla SP+4 rule, so FR/LG/RR/Emerald are
unchanged.

**The begin latch exists.** `release_begin` stores `st.release_snapshot`
(`lua/gen3/client.lua:1304`); `release_done` consumes it and clears it (`:1306-1308`), and it is
cleared on reset (`:1106`). It is cleared on use and on reset, and by nothing else.

**The `sIsMonBeingMoved` deposit gap is downgraded.** `settle_pc` classifies by a **full box
census** — `rescan_boxes()` then `boxed[key]` — not by the site (`lua/gen3/client.lua:531`,
`:541-548`). The site is a *trigger* (`f.pc = true`, `:1443-1444`), never a classifier, so a
moved-mon flag clear cannot publish a wrong identity or lose a mon. Reading `sIsMonBeingMoved`
before the storage call is therefore not required for correctness. The per-build offset
(`&sStorage + 5`) stays in the pack's cursor facts for a future guard.

**Expected moved-mon bypass shape.** It will show `pc_release` **UNPAIRED** — `pc_release_begin`
absent — which is the asymmetry to assert.

in run 2 — **22 registered, 0 rejected, 0 dropped, no handler error**. Run 1 **FAILED** at
