# Polished Crystal and the damage calculator

What SLink's in-battle damage calculator computes for Polished Crystal, what it does not, and
where every claim below comes from. Read this before trusting a number the board shows.

- Dataset: `calc/src/calc/data/polished.js`, generated by `python tools/gen_polished_calc.py`
  (`--check` is the freshness gate; `tests/unit/test_gen_polished_calc.py` is the behavioural gate).
- Server side: `Gen2PolishedAdapter.calc_profile` / `calc_species` / `calc_stats` in
  `server/adapters/gen2_polished.py`; the Manager row is `OPTION_SUPPORT["battle_calc"]`.
- Page side: `calc/data/polished.js` in the engine file list
  (`server/static/calc-preview.js`, `calc/src/normal.template.html`, `calc/src/hardcore.template.html`),
  switched on by `calc.usePolished(dex === 'polished')` in `calc-preview.js` and
  `calc/src/js/slink_bridge.js`'s `_applyCalcGen`.

Source of truth for every mechanic below: the pinned checkout at `data/polished_sources.lock.json`
(polishedcrystal v3.2.3, commit `3fa4319…`), reachable at `$SLINK_WORK_ROOT/cache/polished/src`.

## 1. Why the calculator runs at **gen 3**

Polished Crystal is Crystal's engine with modern mechanics bolted on, so neither of the
calculator's two candidate generations is right on its own. Gen 3 (`calculateADV`,
`calc/calc/src/mechanics/gen3.ts`) is, and each of the four things it decides is checked below.

### 1.1 The damage pipeline is identical

`engine/battle/effect_commands.asm`:

| Step | Source | `BattleCommand_damagecalc` |
|---|---|---|
| `DamagePass1` | `:4427` | `damage = floor(2 * level / 5) + 2` |
| `DamagePass2` | `:4463` | `damage *= power; damage *= attack` |
| boosts | `:4280` | stat stages, then abilities, then burn, then Flash Fire, then crit |
| crit | `:4333` | `x1.5` (`x2.25` with Sniper) |
| items | `:4346` | type `x1.2`, category `x1.1`, choice `x1.5`, Life Orb `x1.3`, Punching Glove `x1.1` |
| `DamagePass3` | `:4473` | `damage /= defense; damage /= 50` |
| `DamagePass4` | `:4485` | `damage += 2` |
| STAB / types | `:1458` | one combined `wTypeMatchup / 16` pass (matchup x STAB x weather) |
| roll | `:1894` | `damage = damage * (85 + random(16)) / 100` |

`calc/calc/src/mechanics/gen3.ts:148` computes
`floor(floor(floor((2 * lv) / 5 + 2) * at * bp) / df) / 50)` — the same chain. Gen 2's
`calculateRBYGSC` differs from Polished in two places that matter (roll and crit, §4).

### 1.2 The damage roll is 85–100%, and gen 3 already models exactly that

`BattleCommand_damagevariation` (`effect_commands.asm:1894`) rolls `85 + BattleRandomRange(16)`,
multiplies and divides by 100. Gen 3's final loop is

```ts
for (let i = 85; i <= 100; i++) result.damage[i - 85] = max(1, floor((baseDamage * i) / 100));
```

Gen 1 and gen 2 roll `217..255 / 255` (`mechanics/gen12.ts:278`), which is a different quantisation
of roughly the same band. Gen 3 is a step function, not an approximation of one.

### 1.3 The physical/special split is per move

`constants/type_constants.asm:31-33` gives every move an explicit `PHYSICAL` / `SPECIAL` /
`STATUS` column, read into `data/games/polished_crystal/moves.json` as `split`. This is the same
data the generator writes as the calculator's per-move `category`, and it is **not** derivable from
a move's type — Psychic-type Bite is Physical in Polished. `calc/calc/src/move.ts:127` derives the
category from the type when the table omits one (that is how gens 1/2 work), so every move row must
carry it; `tests/unit/test_gen_polished_calc.py::test_every_move_carries_polisheds_own_split`
holds that.

### 1.4 The stat formula is Crystal's, not the modern one — and how it is bridged

`engine/pokemon/mon_stats.asm` `CalcPkmnStatC` (`:763`–`:836`) is **pokecrystal's** formula with
modern EVs dropped into the stat-experience slot:

```
de = (base + DV) * 2 + 1 + floor(EV / 4)
stat        = floor(de * level / 100) + STAT_MIN_NORMAL   (5)   + nature pass
max HP      = floor(de * level / 100) + level + STAT_MIN_HP (10) + nature pass
```

`STAT_MIN_NORMAL` / `STAT_MIN_HP` are `constants/battle_constants.asm:81-82`; the nature pass
(`GetNatureStatMultiplier`, `mon_stats.asm:878`) multiplies by 9, 10 or 11 over 10.

The calculator's gen 3 path (`calc/calc/src/stats.ts:130` `calcStatADV`) computes
`2 * base + IV + floor(EV / 4)` — same shape, **half** the DV term. Passing the raw DV would
therefore halve every mon's contribution.

`Gen2PolishedAdapter.calc_stats` bridges it exactly: it sends **`IV = 2 * DV + 1`**, which makes
`2*base + (2*DV + 1)` equal `2*(base + DV) + 1`. The mapping is total — DV 0 → IV 1, DV 15 → IV 31
— so it never leaves the calculator's 0..31 IV range, and it is exact integer arithmetic, not a
correction factor.

Worked example (Bulbasaur, base 49 Attack, DV 15, EV 0, level 50, neutral):
`(49 + 15) * 2 + 1 = 129`; `129 * 50 / 100 = 64` (floor); `+ 5 = **69**`.
The naive encoding would have produced `floor((98 + 15) * 50 / 100) + 5 = 61` — a 12% error.

## 2. What the dataset actually contains

| Table | Count | Built from |
|---|---|---|
| `POLISHED_SPECIES` | 289 + 46 | `species_index.json` `species` + every `kind: "variant"` row, keyed `<base>-<form>` for variants |
| `POLISHED_MOVES` | 255 | `moves.json` — power, type, and the explicit split |
| `POLISHED_TYPE_CHART` | 19 x 19 | `data/types/type_matchups.asm`, default 1x |
| `POLISHED_ABILITIES` | every ability the dex grants | listed, **not** installed (§4.2) |
| `POLISHED_ITEMS` | every holdable item | listed, **not** installed (§4.3) |

**A mono-type mon has ONE type entry.** The pack stores `[T, T]`; `calc/calc/src/mechanics/gen3.ts` multiplies both
defender type slots, so the generator de-duplicates (a repeated slot would square every weakness and resistance;
`test_no_species_repeats_a_type_slot`, and the node probe in `test_gen_polished_calc.py`).

**Cosmetic forms are not rows.** A Unown letter, a Magikarp pattern and the plain form are one mon
in every rule (owner ruling 2026-10-04, `server/adapters/gen2_polished.py`), so the wire never
carries them as separate species ids (`lua/gen2/polished.lua`'s `effective()` folds them) and the
dataset must not invent rows for them. That is what keeps 46 variants from becoming 148 species.

**Variant forms are rows.** A regional form's effective species id *is* its BaseData record index
(292..337, `data/games/polished_crystal/forms_index.json`), so
`Gen2PolishedAdapter.calc_species(295)` returns `Rattata-Alolan` — the exact key the generator
writes. The two spellings are held in step by
`test_the_adapter_and_the_generator_agree_on_the_species_spelling` and by
`test_every_species_and_variant_the_wire_can_send_has_a_dataset_row`.

**The type chart is Polished's, not a re-skin.** It carries a Fairy type
(`constants/type_constants.asm:25`), and it *drops* the Steel resistances to Dark and Ghost that
every other generation has — `type_matchups.asm` has no `DARK, STEEL` or `STEEL, DARK` row, so both
resolve at 1x. A vanilla gen 3 chart would get all three wrong.

## 3. Where the numbers come from, per mon

| Mon | IVs / EVs | Consequence |
|---|---|---|
| The player's party | Real, from the 70-byte party blob the client sends (`lua/gen2/polished.lua` `P.party_entry`) | exact |
| An enemy | **Calculator defaults** (IV 31, EV 0) | see below |

The Polished client's `foe_entry` (`lua/gen2/polished.lua:293`) does not carry `blob_hex`, so
`server.py`'s `_foe_detail` has nothing to decode and the calculator falls back to a maximum-stat
foe. **This is the largest remaining error source**: a foe is treated as if every DV were 15, which
maximises its Defence (and Speed, and Special Defence) and therefore *under*-states how much damage
the player's moves will do. On a level 50 mon that is roughly a 10–15% swing on the printed
percentage, in the direction of "safer than it is".

Closing it needs one field on the wire (`blob_hex` on the enemy entry) plus a battle-view read that
produces it — a client card, not this one. Until then, read the percentages as a floor.

The same default applies to any party mon whose blob the client could not produce. Gen 1 and Gen 2
have the same gap for enemies today; it is a shared-shape limitation, not a Polished-specific one.

## 4. Known approximations

Listed because the calculator is offered for this cartridge and these are the ways it can be wrong.
None of them is hidden in the UI: the Manager's own `battle_calc` row carries a shortened version of
this list.

### 4.1 Critical hits are modelled as **x2**; Polished uses **x1.5**

`effect_commands.asm:4333-4343` multiplies by `3/2` (`9/4` with Sniper). The calculator applies
`baseDamage *= 2` for every gen ≥ 3 (`mechanics/gen3.ts:416`), and the multiplier is hard-coded in
the mechanics module. A critical hit therefore over-states damage by 33%. **Do not trust a crit
number.** This cannot be fixed by data alone; it would need a mechanics module for Polished.

### 4.2 Abilities are not applied

The calculator matches abilities by name (`calc/calc/src/pokemon.ts:62`, `move.ts:114`) and its
gen 3 mechanics implement only a handful by name lookup (`mechanics/gen3.ts:113-122, 409-412`).
Polished's ability set is not installed, and `Gen2PolishedAdapter.supports_abilities()` is `False`
in any case: the ability slot lives in the personality byte
(`server/adapters/polished_codec.py` `_head`), which the mon key does not carry and which the wire
never sends. So no ability is assumed, and none is applied — even for the common ones
(Huge Power, Adaptability, Thick Fat, Multiscale).

The ability/item tables are deliberately **not** swapped into the calculator's data: its
`AbilityData` / `ItemData` carry the effect multipliers, and replacing them with name-only entries
would delete working behaviour for every ability and item Polished shares with gen 3.

### 4.3 Held-item boosts are mostly not applied

`items.json` carries Polished's `held_effect` column, and the engine applies:

| Item effect | Multiplier | Modelled? |
|---|---|---|
| `HELD_TYPE_BOOST` | x1.2 | no — a gen 5+ mechanic `mechanics/gen3.ts` has no code for |
| `HELD_CATEGORY_BOOST` | x1.1 | no, same reason |
| `HELD_CHOICE` | x1.5 | no, same reason |
| `HELD_LIFE_ORB` | x1.3 | no |
| `HELD_PUNCHING_GLOVE` | x1.1 | no |
| `HELD_ASSAULT_VEST` | defender x2/3 | no |
| `HELD_EXPERT_BELT` | x1.2 on a super-effective hit | no |
| `HELD_METRONOME` | (5+n)/5 | no |
| Leftovers, Life Orb recovery, berries, status berries | — | no (not damage) |
| Thick Club, Light Ball, Metal Powder | x2 / x2 / x1.5 | **yes** — `mechanics/gen3.ts` implements these |

So a Choice Band, Life Orb or Assault Vest holder is under-stated, and a Thick Club holder is
correct. This is a cap of the gen 3 mechanics module, not of the dataset.

### 4.4 Natures are not applied

Polished has 25 natures in the vanilla order (`constants/nature_constants.asm`) and the mon's
nature is a real field of the record. It cannot reach the calculator: `calc_nature(key)` takes only
the mon key, and Polished's key (`DDDDDD:OOOO:SSS:TT`) carries no personality. Every mon is
therefore calculated with a neutral nature — a systematic error of up to 10% on one stat. Fixing it
means widening the shared `calc_nature` signature (or passing the nature through `calc_stats`),
which is a server-contract change outside this card.

### 4.5 Ground hits Flying neutrally

`type_matchups.asm:66` comments out `GROUND, FLYING, NO_EFFECT` with the note "checks airborne
state instead"; the engine decides that row from the target's airborne state at runtime. The
generated chart therefore has Ground → Flying at 1x, which is right for a grounded target and wrong
for an airborne one.

### 4.6 Move effects are data-light

The dataset carries power, type and split. Secondary effects, drain, recoil, multi-hit,
priority, status and accuracy are **not** in it — a move that the cartridge would make miss, or that
drains, computes as a clean hit. The calculator's own Gen 3 move table has these for the moves it
knows, but Polished's own table replaces it, so nothing falls back. Draining moves in particular
under-state the foe's HP loss.

### 4.7 One gen slot, two games

Polished swaps the calculator's **gen 3** slot, which is also FireRed/LeafGreen/Emerald's. Both the
board preview and the full page re-assert `calc.usePolished(...)` on every payload and every
render, so a run never sees the other's tables — but only because they always call it. A new caller
that builds a `Generation(3)` without calling `usePolished` gets vanilla gen 3 data silently.

### 4.8 Doubles, terrain, and other modern fields

`calc-preview.js` builds the field as `Singles` unless the battle state says otherwise. Polished has
no terrains, no Terastallisation, and no Dynamax. Triple battles, if the cartridge has them, are
untested here.

## 5. What is UNVERIFIED

These are open, and none of them is asserted anywhere in the code as true:

- **No cartridge has been run against this calculator.** Every mechanic claim here is read off the
  pinned source and the pinned packs; none has been confirmed by a real in-battle damage number.
  `tests/unit/test_gen_polished_calc.py::test_hand_computed_damage_matches_the_cartridge` pins the
  *arithmetic* against a by-hand transcription of `BattleCommand_damagecalc`, which catches a
  transcription error but cannot catch a misread of the engine.
- **The calculator's own engine has not been executed here** (`calc/dist` is not built in this
  checkout), so the claim in §1 that `calculateADV` reproduces the cartridge's numbers is a reading
  of `calc/calc/src/mechanics/gen3.ts`, not a measured comparison. `tests/unit/test_calc_bundle.py`
  and `tests/unit/test_calc_preview.py` skip without a build; the follow-up is one probe test of the
  same Bulbasaur/Acrobatics case driven through the real engine, asserting `[44, 52]`.
- **Special moves are not spot-checked by arithmetic.** The spot check is a Physical move; the
  Special branch differs only in which of `spa`/`spd` the engine reads
  (`mechanics/gen3.ts:144-145`), and the dataset's per-move `category` is what selects it. No
  hand-computed Special case is pinned yet.
- **No prep/trainer setdex ships for Polished.** `calc_profile()` deliberately omits `sets`, so the
  calculator's Prep tab stays hidden for this cartridge (`calc/src/js/slink_bridge.js`
  `_maybeLoadGameSets` → `_supportsPrepTab`). `data/games/polished_crystal/trainers.json` already
  carries level, species, item, moves and (for some) EVs per mon, so a
  `calc/src/js/data/sets/games/PolishedCrystal.js` is a small generator extension away — it is a
  follow-up, not a gap in the damage model.
- **The generated dataset has never been byte-compared to the packs by a run of
  `tools/gen_polished_calc.py`.** Its unit tests cover that, but only once they have been executed
  in an environment with the pinned checkout present.
