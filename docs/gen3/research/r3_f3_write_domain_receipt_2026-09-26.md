# R3-F3 receipt: FR/LG write-domain audit (2026-09-26)

Closes the gap in `randomized_gen3_design.md` §5 risk 7(a). It applies pureRGB's T6 standard
(`docs/purergb/PLAN.md` A5 / G5) to FR/LG: disabled settings write nothing, enabled settings write
only inside their allow-listed domains, and 0 bytes land anywhere else.

## What was built

- `server/upr_gen3_write_domain.py`:
  - `domains_for_spec(spec)`: which domains an FR/LG spec enables, using `Randomizer.randomize`'s
    own conditions.
  - `audit()`: diffs the clean ROM against the output. Every changed byte must fall in an enabled
    domain; every stray byte is named by the domain(s) that hold it, or marked `unattributed`.
  - `check_output()`: the pipeline's one call.
  - `build_model()`: builds the data file (see below).
- `data/games/gen3_frlg/upr_write_domains.json`: 39 domains per title. Every component carries a
  `source` naming the fact it comes from. The file is generated by
  `python -m server.upr_gen3_write_domain --write` from three inputs:
  - the pinned jar (sha256 `28292b59...`): its own `gen3_offsets.ini` `[Fire Red (U) 1.0]` and
    `[Leaf Green (U) 1.0]` sections, and its IPS code tweaks, read from the jar;
  - the clean pinned ROMs, walked the way `Gen3RomHandler` walks them (its locators,
    `preprocessMaps`, the wild headers, the trainer table, the ±500-byte text-pointer search);
  - the pret `.sym`, used for the free-space gap and to cross-check the tutor compatibility table.

  A ROM-backed test rebuilds the file and requires it to be byte-equal to the committed one.
- `tools/upr_write_domain_diff.py`: new Gen 3 mode. Example:
  `--title firered|leafgreen --clean C --out O --log O.log`, or pass `--enable DOMAIN` instead of
  `--log`.
- `tests/unit/test_upr_gen3_write_domain.py`: 128 rows (ROM-free model rows plus ROM/jar rows,
  110 of them the per-option isolation matrix).

## Review fixes (OMP cx-8361dab2, card R3-F3b)

- **`tutor_compat` does not write the cartridge header; the reviewer was wrong about the offset.**
  `MoveTutorCompatibility` is absent from the jar's `gen3_offsets.ini` FR/LG sections, but
  `Gen3RomHandler.loadROMInfo` (line 446) puts it into `romEntry.entries` for every non-R/S ROM as
  `MoveTutorData + 2*MoveTutorMoves`. `getValue` therefore never returns 0 for it. That gives FR
  0x459B7E and LG 0x45959E, which is exactly the table pret's `CanLearnTutorMove` reads: its literal
  pool at 0x120C30 holds 0x08459B7E. The fork's own BPRE hack path reads that same pointer.
  - Fork runs with only tutor compat on (FR and LG; random, prefer_type, full and tutor_sanity), plus
    a control with everything off:
    - `clean[0:0x1000]` vs `out[0:0x1000]`: **0 bytes changed** in all 10 runs.
    - The modelled range changed 768/762/746/2 bytes (FR) and 765/764/746/2 (LG).
    - With `tutor_compat` removed from the enabled set, every other changed byte stays inside
      `baseline`.
  - Fix: provenance only. The source now cites `loadROMInfo`, and the builder asserts the
    `CanLearnTutorMove` cross-check. **No allowlist change is needed.**
- **Per-option isolation test** (`test_each_option_alone_writes_exactly_its_domains`, needs Java):
  - Scope: every writing FR/LG option alone at every value, with catch-rate at every tier. That is
    55 cases per title, 110 fork runs, about 45 s.
  - Each run must have 0 stray bytes, and every enabled domain must receive a byte that no other
    enabled domain explains.
  - It caught two real widenings in 7d6c76ea:
    - catch-rate tier 5 granted `catch_rate`, but `randomizeCatchRates` tier 5 only calls
      `enableGuaranteedPokemonCatching`;
    - `tutors` granted `free_space` and the tutor text sites, but `setMoveTutorMoves` writes texts
      only for sites `preprocessMaps` located, and with tutors alone the maps have not been walked
      yet (Randomizer order is TMs, tutors, then the rest). These moved to a new `tutor_text` domain,
      enabled by tutors AND tms.
  - Revert check: granting `free_space` to shops turns all 6 shops cases red.
- **`free_space`:**
  - The tail grant is dropped. Every `freeSpaceFinder` call scans forward from FreeSpace.
  - The component is `packed`. `audit` admits only changes packed from FreeSpace, meaning at most
    `PACKED_MAX_GAP = 5` unchanged bytes precede each changed byte, counting from FreeSpace. Bytes
    that fixed enabled domains already explain are ignored, such as the Marowak, roamer and music
    IPS at 0xA80000.
  - Why this is the fork's behaviour: `freeSpaceFinder` returns
    `(first run of amount+5 0xFF + 5) & ~3`, so the first allocation starts at FreeSpace+4. Each
    later one starts 2–5 bytes past the previous allocation's 0xFF terminator.
  - Measured on 20 runs (tms, natdex, tms+tutors+natdex, everything): first write at +4, largest
    gap exactly 5.
  - A write past the packed run is named `free_space (not packed from 0x800000)`.
  - Revert check: `PACKED_MAX_GAP = 4` turns the tms and allowed/all-options rows red.
- **`field_items` split** into `field_tms` (the current item isTM) and `field_regular` (isAllowed
  && !isTM), mirroring the Gen 1 item-pool rule. `test_field_item_pool_is_the_forks_own`
  re-derives both pools from the fork source's `Gen3Constants.setupAllowedItems`.
- **`check_output`:**
  - OSError (a missing model or ROM) is raised as `UprPipelineError`.
  - A non-FR/LG cartridge gets a message naming the covered titles.
  - It refuses when the jar's sha256 differs from the model's `jar_sha256`. The jar is the new
    `jar=` argument, defaulting to `find_upr_jar()`.
  - The ability-overlap guard matches the component ids `ability2_normalisation` and
    `deoxys_stats`.
  - A module-teardown guard fails the run when `SLINK_GEN3_ROMS` is set but every selected ROM/jar
    row skipped (revert-checked with an untrusted `SLINK_UPR_JAR`).

## Pipeline wiring (not applied: `server/upr_pipeline.py` is leased elsewhere)

In `prepare_pair`'s FR/LG branch, right after `info["sites_intact"] = True` (wired on
claude/gen3-rand-fix; it should pass the jar it actually ran):

```python
            info["write_domain"] = upr_gen3_write_domain.check_output(
                sources[player], info["output"], info["spec"], jar=jar)
```

It needs `from server import upr_gen3_write_domain` at the top of the module. The module does
not import `upr_pipeline` at import time, so this creates no import cycle. `check_output` raises
`UprPipelineError` naming the domains the stray bytes fall in.

## Findings for the owner / other lanes

1. **The baseline writes into the forbidden `abilities` and `base_stats` columns, even with every
   setting off.** This is the ability-normalisation blocker from the Codex review; the audit makes
   it explicit rather than fixing it. A test pins that allowed domains meet forbidden tables ONLY
   at these two normalisations. Once the fork stops writing them, drop them from `baseline` and
   that test tightens itself.
2. **`obedience_evo_code` is a CODE write that the 21-site check never covered.**
   `attemptObedienceEvolutionPatches` runs whenever wild, starters or statics are randomized. It
   makes Deoxys and Mew obey and lifts the Kanto-dex gate on level and stone evolution. It is
   allowed today because every default preset triggers it; this is a gameplay change the owner
   may want to rule on.
3. **Trainer repointing is not granted.** No allowed option grows a party. If a future option
   does, the audit refuses it by name instead of passing it silently.

## Not verified

- **Range level only.** The audit does not check values. A pointer written inside an allowed
  domain (for example a TM text site) is not checked for where it points, and free-space
  contents are not validated.
- **Scope.** Only FR/LG 1.0 (U) are covered. FR/LG 1.1, other regions and Emerald are not.
- **Tightness is per domain, not per component.** The isolation test proves that each enabled
  domain receives bytes. It does not prove that every component inside the domain does (for
  example, TM item-description pointers inside `tms`).
