# FR PC flow: RAM witnesses per stage (OMP gen3-O4, cx-fee363a7, 2026-09-23)

Read-only derivation from pret pokefirered c75f3523 + data/gen3/pret/pokefirered.sym. Coordinator spot-check: all 15 named addresses match the sym. Note: the sym has TWO sMenu statics (0x020399C0 and menu.c's 0x0203ADE4); the multichoice cursor is menu.c's sMenu.cursorPos = 0x0203ADE6. Reviewer ground truth for card C3-38.

SUMMARY
Every stage of the FR PC flow has a Lua-observable RAM witness, derived independently from pret c75f3523 plus data/gen3/pret/pokefirered.sym: the script owning the field is sGlobalScriptContextStatus/sLockFieldControls, the 'Which PC' list is the task Task_MultichoiceMenu_HandleInput (0x0809CC98) whose cursor is menu.c's sMenu.cursorPos (0x0203ADE6) and whose result lands in gSpecialVar_Result (0x020370D0 = VAR_RESULT, proven from the ROM's gSpecialVars table), the storage main menu is Task_PCMainMenu (0x0808C39C) with its row in task data[1], the deposit party-select is gStorage->boxOption (deref 0x020397B0; OPTION_DEPOSIT=1) plus the file-static sCursorArea/sCursorPosition (0x02039820/0x02039821), the STORE popup is Task_OnSelectedMon (0x0808D878) with the same shared cursor, and the chooser is Task_DepositMenu (0x0808DD88) with sChooseBoxMenu->curBox and the confirm byte sDepositBoxId (0x020397B6). Two of the card's framings are wrong and are corrected below: the 'See you later' string is the SEE YA! row's *description* (not an exit message), and leaving the storage menu returns to the PC-owner list, so the field needs a second step (LOG OFF or B-cancel).

FINDINGS
1. STAGE-3 WITNESS PROVEN FROM ROM BYTES, not just from source comments. `gSpecialVars` (sym:13124, ROM 0x0815FD0C) is a table of u16 pointers; entry 0x0D (= VAR_RESULT, include/constants/vars.h:328) reads 0x020370D0, which is `gSpecialVar_Result` (sym:231). So reading the u16 at 0x020370D0 IS reading VAR_RESULT. Command used: `struct.unpack_from('<I', rom, 0x15fd0c + 0x0D*4)` -> 0x020370D0. Confidence: certain.
2. THE SCRIPT-OWNS-THE-FIELD INVARIANT IS EXACT AND PER-FRAME. `ScriptContext_SetupScript` (src/script.c:347-357) locks at :355; `ScriptContext_RunScript` (:326-345) re-asserts `LockPlayerFieldControls()` every frame while RUNNING (:334) and on the script's end sets `CONTEXT_SHUTDOWN` + `UnlockPlayerFieldControls()` (:339-340). So `sGlobalScriptContextStatus != 2` and `sLockFieldControls == 1` are the same fact, and the PC interaction path reaches it (`TryStartInteractionScript`: field_control_avatar.c:371-384 -> ScriptContext_SetupScript at :382; that path deliberately suppresses SE_SELECT for EventScript_PC at :378-381, and `GetInteractedMetatileScript` returns EventScript_PC for a PC metatile at :515-519). One caveat worth knowing: `ScrCmd_lockall` (scrcmd.c:1195-1207) does NOT set sLockFieldControls -- it freezes objects; the lock comes from ScriptContext_SetupScript/ScriptContext_Enable (script.c:369), not from the script's own `lockall`. Confidence: high.
3. THE CARD'S STAGE-7 FRAMING IS WRONG IN TWO WAYS. (a) 'See you later' is `gText_SeeYaDescription` (strings.c:681), the *description* line shown while the cursor sits on the SEE YA! row (`gText_SeeYa` = "SEE YA!", strings.c:676; both in `sMainMenuTexts[OPTION_EXIT]`, pokemon_storage_system_menu.c:42) -- it is not an exit message and prints nothing on the way out. (b) Choosing SEE YA! (or pressing B) in the storage menu calls `UnlockPlayerFieldControls(); ScriptContext_Enable(); DestroyTask()`, and the script loops `goto EventScript_PCMainMenu` (pc.inc:50-55) -- it returns to the PC-owner list, NOT the field. The field needs the second step: LOG OFF (switch case 4) or B-cancel (VAR_RESULT 127) -> `EventScript_TurnOffPC` -> `releaseall` + `end` (pc.inc:100-107), which is when status goes SHUTDOWN and the lock clears. Confidence: high.
4. THE 'Which PC' LIST IS A TASK, NOT A GLOBAL, and the row count is flag-dependent. `CreatePCMenu` (script_menu.c:977-984, `def_special CreatePCMenu` at data/specials.inc:273) -> `CreatePCMenuWindow` (:986-1036) -> `Menu_InitCursor(..., numItems, 0)` + `CreateMCMenuInputHandlerTask` (:1034) -> `CreateTask(Task_MultichoiceMenu_HandleInput, 80)` (:797). numItems is 3 (no Pokédex), 4 (Pokédex, the driver's case), or 5 (FLAG_SYS_GAME_CLEAR) by the branches at :1006-1034, and the live row count is readable as `sMenu.maxCursorPos + 1` -- useful to tell the three cases apart without reading flags. Confidence: high.
5. DEPOSIT vs WITHDRAW IS `gStorage->boxOption`, and the party cursor is a FILE STATIC. `EnterPokeStorage(boxOption)` stores it (tasks.c:412-429) and `InitCursor()` (data.c:68-84) puts the cursor in the party area iff `boxOption == OPTION_DEPOSIT` else in the box area, then zeroes `sCursorPosition` (the party cursor wraps to PARTY_SIZE at data.c:1465-1470 and A on that row is the CLOSE BOX entry, :1504-1510). Those three bytes (deref 0x020397B0 +0x00 state, +0x01 boxOption; 0x02039820 sCursorArea; 0x02039821 sCursorPosition) are the whole 'choosing a party mon' state; `showPartyMenuState`/`partyMenuY` are only the list's rendering and need a struct-offset walk (see UNKNOWN). Note the FRLG names: there is no sPSSData/sStorage in FRLG -- the pointer is `gStorage` and the cursor pair are file statics in pokemon_storage_system_data.c:15-22. Confidence: high on the names/offsets of the first two bytes and the cursor pair; the rendering fields unverified.
6. POPUP ROW 0 IS STORE BY CONSTRUCTION, and the 'selected row' the task switches on is a text id, not an index. `SetMenuTextsForMon` (data.c:1755-1805) adds `MENU_TEXT_STORE` first for OPTION_DEPOSIT, then SUMMARY/MARK/RELEASE/CANCEL; `HandleMenuInput` (data.c:2123-2150) maps A -> `Menu_GetCursorPos()` and then `input = gStorage->menuItems[input].textId` before returning, and `Task_OnSelectedMon` (tasks.c:935-1005) switches on that textId (MENU_TEXT_STORE=1, ... internal.h:27-58). So the cursor index is menu.c's sMenu.cursorPos and the semantic row is menuItems[cursor].textId -- if you only have the offset-free bytes, `Task_OnSelectedMon alive + cursorPos == 0` is already STORE. Confidence: high.
7. THE CHOOSER'S LIVE BOX IS A DEREF THROUGH A POINTER STATIC. `LoadChooseBoxMenuGfx(&gStorage->chooseBoxMenu, ...)` sets `sChooseBoxMenu = menu` (pokemon_storage_system_menu.c:423-438), so `sChooseBoxMenu` (sym:306, 0x020397AC, size 4 = pointer) aliases the struct inside gStorage; `HandleBoxChooseSelectionInput` (:463-486) returns `sChooseBoxMenu->curBox` on A. The confirmed-deposit byte is `sDepositBoxId` (sym:310, 0x020397B6), written only when `TryStorePartyMonInBox` succeeds (tasks.c:1214-1222). Confidence: high on the mechanism and the statics; the curBox offset itself is computed (see UNKNOWN).
8. THE R9 DOC (docs/gen3/research/fr_pc_flow_and_pc_move_sites.md) IS RIGHT ON THE FLOW AND SILENT ON RAM. `grep -n "VAR_RESULT|gSpecialVar|gStorage|sCursor|Task_PCMainMenu|Task_DepositMenu|cursor"` over it returns only the flow/press-count rows and its two Task_* addresses for the RR cross-check: no result variable, no cursor, no gStorage, no task-data field. Its positive claims I re-checked hold: five A inputs (pc.inc:1-12,20-24,44-55 + `msgbox` waits), the storage menu order 0 WITHDRAW..4 SEE YA (internal.h:17-24 + sMainMenuTexts menu.c:37-43), the popup order STORE/SUMMARY/MARK/RELEASE/CANCEL (:1761-1805 -- its own citation), the extra box-chooser confirm (Task_DepositMenu state 0/1), the party-area start at slot 0 (InitCursor), `Task_PCMainMenu` 0x0808C39C / `Task_DepositMenu` 0x0808DD88 / `TryStorePartyMonInBox` 0x080930E4 (sym:6125,6164,6324), and count-recomputed-on-exit. Its one missing premise is the result path: the doc never names VAR_RESULT/gSpecialVar_Result, so a reader cannot tell 'the choice was consumed' from 'the list is still up' -- which is exactly the 27b stall. Confidence: high.
9. 27b's STALL IS VISIBLE THREE WAYS, which is what makes a witness-based menu open possible: the multichoice task stays alive in gTasks with cursorPos 0, gSpecialVar_Result keeps its previous value (nothing resets it before this list -- `ScriptMenu_YesNo` sets SCR_MENU_UNSET, this menu does not), and `EventScript_PCMainMenu`'s `waitstate` (ScrCmd_waitstate -> ScriptContext_Stop, scrcmd.c:127-131) has stopped the script context while the multichoice task has not yet called `ScriptContext_Enable` (script_menu.c:837-840). Confidence: high.

DISAGREEMENTS
- The card says stage 7 is "leaving storage and the 'See you later' text back to the field". As written, that implies one step and a message; in FRLG it is two steps and no message (finding 3). A reviewer using the card's framing would write a witness that cannot reach the field.
- The card's stage 5 asks which variable "says choosing a party mon" of "sPSSData / sStorage". Neither name exists in FRLG; the answer is `gStorage->boxOption` plus the file-static cursor pair (finding 5). If the reviewer greps for sPSSData/sStorage in the FR pack they will find nothing and may conclude the witness does not exist.
- I expect the orchestrator to have assumed `lockall` is what sets the field-controls lock (the pack's predicate is named field_controls_locked). It is not: the lock comes from ScriptContext_SetupScript/ScriptContext_Enable/ScriptContext_RunScript (finding 2).

UNKNOWN / UNVERIFIED
- `sChooseBoxMenu->curBox` at +0x244 is COMPUTED from struct ChooseBoxMenu (internal.h:228-241), not byte-verified: no compiler was run. A build that emits offsets (or a Lua print of `offsetof`-equivalents) would settle it. The confirm byte `sDepositBoxId` needs no offset and is the safer witness.
- `gStorage->showPartyMenuState` / `partyMenuY` offsets: the struct is large (pointers, a nested UnkUtil/UnkUtilData, several 512-byte arrays) and I did not verify a computed offset, so I do not offer them; if the reviewer wants a party-list-rendering witness, generate the offset table instead of hand-counting.
- Whether `EventScript_PC`'s `lockall` is load-bearing for anything the driver needs (it freezes objects; the lock comes elsewhere) -- not needed for the witnesses, but the two are easy to conflate.
- The exact frame at which each message appears/vanishes is not observable from the named globals I found (the script-context struct that holds the bytecode pointer is not in the .sym): stage 1 is observable as 'a script owns the field', not as 'message N is up'. The menu tasks and the help context are what give message-level granularity.
- I did not re-verify the doc's engine-site pins (pc_deposit 0x08093164 etc.); those are SOURCE_BYTE_PIN contracts from another card and are outside this witness question.

RECOMMENDATION
Build the C3-38 waiter as a small state machine over: the script pair (status/lock) -> the multichoice task + sMenu.cursorPos -> gSpecialVar_Result after that task disappears -> Task_PCMainMenu + data[1] -> gStorage->boxOption + sCursorArea/sCursorPosition -> Task_OnSelectedMon + sMenu.cursorPos -> Task_DepositMenu + sDepositBoxId -> status==SHUTDOWN + lock==0 with no PC task, with a per-stage timeout that names the stage it stalled in (the stalls you have seen are all 'the task that should have gone is still there'). Poll, never sleep-and-press: every one of these is a byte you can read at frame end, and gSpecialVar_Result must never be trusted without the multichoice task's disappearance. Also use `sMenu.maxCursorPos + 1` to assert which menu is current rather than assuming 4 or 5 rows.
