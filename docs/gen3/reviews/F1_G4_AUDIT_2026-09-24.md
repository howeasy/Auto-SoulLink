### Q1. Can any plan other than exactly P+H or exactly Explode+H pass `battle_commit_handoff`?

Through the client: **no.** The policy path is entered only when `touches_slots(plan)` is true
(`safety.lua:372`), and then `check_handoff_plan` (`:326-339`) requires the plan to equal, row for row
(address, width, value; `matches` `:311-325`), either `p_rows()` + commit + hand-off, or
`explode_rows(with_moves)` + commit + hand-off for `with_moves` in {true, false}. Length must match, so no
extra or missing row passes. Battler ≠ 0 is refused twice (`handoff_entry` `:241`, the assert `:327`).
`test_g5_rr_every_other_explode_shape_is_refused` covers 9 shapes x 2 kinds.

Through the pack (the policy trusts `pack.battle.handoff.explode.head`): two admissions remain,
recorded as M4/L5 below, neither reachable from a generator-produced pack:

- `valid_rows(h.explode.head, true)` (`:217-236`) checks each row's shape but not the set. A pack whose
  every explode row carries `group: "moves"` makes `explode_rows(false)` empty, so `[comm, hand-off]` is
  admitted, which is the R1 L1 hazard (stale `gChosenActionByBattler[0]` replays last turn's action). The
  generator always emits four non-moves rows, and `test_g5_rr_handoff_carries_the_exact_explode_head_and_frlg_none`
  pins the committed pack, so this is pack-trust, not a live hole.
- Nothing ties the explode rows to the P head (they may overlap in address); harmless today.

### Q2. Is FR/LG Explode byte-identical in plan and policy?

**Yes.**
- Pack: `904c134c` touches only `data/games/gen3_rr/write_checkpoint.json`; the FRLG pack has no
  `handoff.explode` (`test_g5_rr_handoff_carries_the_exact_explode_head_and_frlg_none`,
  `test_g5_frlg_packs_admit_no_explode_handoff`).
- Client: `commit_plan` (`client.lua:625-651`) is only reachable when `explode_capable`
  (`:547-548`: needs `CHOSEN_MOVE_ADDR` and `BATTLE_COMM_ADDR`); the FRLG profile has
  `CHOSEN_MOVE_ADDR = 0` and `BATTLE_STRUCT_PTR_ADDR = 0` (read from `data/games/gen3_frlg/profile.json`),
  so on FR/LG `force_explode` never builds a commit plan, before or after the commit. Even if it did,
  `policy:handoff_entry(0, "explode")` returns nil on FR/LG (`assert(type(h.explode) == "table")` fails
  inside the pcall), so the plan would be the pre-commit plan.
- Policy: for a plan with no slot write `touches_slots` is false and neither the hold nor the hand-off
  clause is added (`:372-384`); FR/LG packs carry no `commit_hold`. `test_frlg_battle_commit_policy_is_unchanged`
  pins it.
- Wire: the FR/LG half of `test_world_force_explode_is_handled_at_least_as_force_faint_on_vanilla_frlg`
  is unchanged by the commit (only the RR half changed).

### Q3. Is the Explode+H plan order engine-correct on RR (CFRU)?

**As far as source can show, yes; it is P+H's tail on Variant 3's head, and neither has an RR live receipt.**
- The plan is written whole inside one paused Lua call (`writes:write_plan`, R1 confirmed no TOCTOU), so
  row order is a policy convention; the engine sees the final state: `gBattleMons[0].moves[*] = 153`,
  `pp[*] = 5` (first commit only), `gChosenActionByBattler[0] = 0` (USE_MOVE), `gChosenMoveByBattler[0] = 153`,
  `gBattleStruct->chosenMovePositions[0] = 0`, `moveTarget[0] = 1`, `gBattleCommunication[0] = 3`,
  `gBattlerControllerFuncs[0] = PlayerBufferExecCompleted`.
- With comm = 3 (pokefirered has no `STATE_TURN_START_RECORD`, so 3 = `STATE_WAIT_ACTION_CONFIRMED_STANDBY`),
  HTAS waits for exec bit 0, which the hand-off clears on the next `BattleMainCB1` pass (scope §3.2 steps
  1-3, PROVEN by disassembly on RR), then emits `LINK_STANDBY_MSG`. State 3 reads neither `gBattleBufferB`
  nor the menu cursor, so the skipped states 1-2 (which are where CFRU's mega/Z/dynamax bytes come from
  buffer B) do not matter more than they did for the old client's Variant 3, which is the head this shape
  copies verbatim (`lua/memory_gba.lua:1318-1345` constants, `tools/gen_gen3_write_checkpoint.py:800-806`).
- The "comm then hand-off" ordering rule (scope §3.2, "with comm = 1 the stale buffer-B action replays")
  is enforced by `matches` placing commit and hand-off as the last two rows.
- What is *not* shown anywhere: a live RR run of either P+H or Explode+H. The draft correctly parks both
  at G5 (`8103ddec` fixture, rulings 19-20). R1's L5 ("Explode resolves later than P on RR") is closed by
  this commit; the ordering consequence (Explode now commits at the first parked menu, the old client's
  behaviour) matches protocol item 34 and ruling 19.

### Q4. Does the generator's "Explosion PP 5 in both RR ROMs" check make sense?

**Partly. It is a pin-drift tripwire, not a proof the plan needs, and its failure mode is silent (M5).**
- `explode_head` (`gen_gen3_write_checkpoint.py:816-820`) reads one byte at
  `BATTLE_MOVES_ADDR + 153*12 + 4` in RR clean and companion and requires 5. Nothing in the plan or the
  engine consumes the ROM's PP for Explosion: the plan writes `pp = 5` into `gBattleMons`, `ppreduce`
  decrements that copy (and the party's slot-0 move, a Variant-3 property inherited from the old client),
  and `explode_step`'s witness is `pp0 < 5` on the battle copy (`client.lua:686`). So the check proves
  "RR's move table sits where the profile says and move 153 still has vanilla PP", which is a reasonable
  sanity pin, but the same byte would read 5 for any 5-PP move if the table were shifted by whole entries.
  A check that the move is Explosion (e.g. its effect byte at `+0`, `EFFECT_EXPLOSION` in CFRU, or the
  move-name entry) would pin what the shape actually relies on.
- If the byte ever differs, the generator drops only the Explode shape (`unverified` row) and `commit_plan`
  builds a plan with no tail; on RR `commit_hold` then refuses every Explode commit. Explode Mode on RR
  silently reverts to "held until switch-out" with no test failing except the pack-equality test
  (`test_g5_rr_handoff_carries_the_exact_explode_head_and_frlg_none`), which does run in the suite, so
  the drift is caught at `--check` time rather than at runtime. Acceptable, but say so in the generator.

  battler takes the `"hold", "active battler"` branch (`client.lua:796-806`) while `force_faint` takes P+H,

  without an owner ruling.
