## Findings

### MEDIUM

**M1. The policy admits a hand-off for battlers 1, 2 and 3; only the client limits it to battler 0.**
Location: `lua/gen3/safety.lua:213-221` (`handoff_entry` accepts battler 0..3) and `:242-255` (`check_handoff_tail`).

- **Why it matters.** All seven battle clauses pin battler 0: `battle_comm_0`, `battle_exec_flags_input == 1`, and slot 0 in `battle_input_controller`. The commit guard reads `comm[battler]`. So for battler b ≠ 0, the slot the hand-off writes (`0x03004FE0 + 4b`) is not a word any clause checks. The "same word the controller clause checks" guard therefore holds for battler 0 only.
- **Repro.** At the parked world, in all four packs (FR, LG, RR clean, RR companion), `{battler = 2, plan = p_plan(battler = 2)}` with `comm[2] = 0` returns `verified battle_commit` with no failing clauses.
- **Failure scenario.** A doubles battle where battler 0 is parked. The partner battler 2 is still at `STATE_BEFORE_ACTION_CHOSEN` (0), so the guard `0 < 3` passes. A wrong battler mapping, or a later client edit that relaxes `client.lua:795-796` (`battler == 0 and battlers_count == 2 and not is_doubles`), gets a Perish commit on the partner admitted. The partner is then KO'd at end of turn by a write the policy approved.
- **Context.** Scope §5.2 and §5.3 say "singles, battler 0" and "the policy enforces the rule from the plan itself instead of trusting a flag". Today only the client enforces the battler-0 part.
- **Fix.** In `check_handoff_tail`, `assert(battler == 0)`. Optionally also require `entry[1] == ctrl.address + ctrl.offset`, so the slot written is exactly the word the clause checks.

### LOW

**L1. The hand-off clause checks only the tail; the head of the plan is not checked.**
Location: `safety.lua:242-255`. This follows the spec (§5.3 lists only tail conditions), so it is a spec gap rather than a code bug.

- These plans are admitted, and on RR they lift `commit_hold` (repro):
  - `[comm = 3, hand-off]` alone. This leaves `gChosenActionByBattler[0]` stale, so last turn's action replays. That is the exact hazard the §3.2 ordering rule exists to prevent.
  - `explode_plan() + [hand-off]`.
- The claim that Explode stays held on RR is true only because `commit_plan` (`client.lua:626-651`) has no tail. The policy does not tell P from Explode.
- The client builds every plan, so none of these is reachable today.
- **Optional fix.** Require the head to be exactly P's three rows for the same battler.

**L2. `touches_slots` checks only the literal slot range, not its IWRAM mirrors.**
Location: `safety.lua:228-239`. The check covers `0x03004FE0..0x03004FEF`. IWRAM repeats every `0x8000`, so a write to `0x0300CFE0` reaches the same physical slot.

- **Repro.** On FR, a plan with `[0x0300CFE0, 4, x]` is not treated as a slot write. No hand-off clause runs and the plan is admitted.
- On RR the hold still refuses such a plan.
- The client cannot produce this plan. It matters only if the policy is expected to be the boundary.

**L3. Several fields in the carrier's log receipts are literal constants, not measured values.**
Location: `lua/tests/duo/scenario_gen3_linked_faint_active.lua:96` and `:117`.

- The literal fields are:
  - `ACTIVE_KO ... inputs=` (printed as `hammer and -1 or 0`) and `hp_writes=0`;
  - `HANDOFF ... exec_bit0=0` and `from=`;
  - `ACTIVE_FAINT_SITE ... battle_hp=0 party_hp=0`.
- As a result, the Python side of `tools/e2e_duo.py:1433` `active_faint_chain`, including its `inputs=0` check and the model test's "red on inputs=1", cannot fail on real Lua output.
- This does not make the carrier vacuous. The real checks are the Lua `fail()` guards in `observe()`, and those read the engine and are model-tested by name. The Python layer contributes only ordering and presence.
- **Fix.** Print the measured values: `ctx.inputs() - in0`, the count of HP-address writes, and `s.exec & 1`.

**L4. A carrier watcher that throws is silently dropped.**
Location: `lua/tests/duo/duo_gen3_main.lua:583-586`. `pcall(watchers[i])` removes a watcher that errors and logs nothing.

- The P+H observer would then stop without setting `o.fail`, and the scenario would time out with a generic reason ("the client never committed P+H"). It is a FAIL, not a false PASS, but the real cause is lost.
- **Fix.** Log the error.

**L5. On RR, force_explode now resolves later than force_faint.**
Explode is unchanged on every title:
- On FR/LG, `touches_slots` is false for `commit_plan`, so no new clause runs.
- On RR, `commit_hold` stays in place.
- This is confirmed by `test_ph_rr_explode_commit_plan_stays_held` and the `test_protocol_conformance` block.

But on RR a force_faint is now an immediate Perish KO, while a force_explode stays held until switch-out. This is the §5.7 follow-up and is documented, so it is recorded here only.

**L6. The Perish timer write changed for every pack, including packs without `handoff`.**
Location: `client.lua:721`. The timer row changed from `0` to `current & 0xF0` for every pack, not only packs with `battle.handoff`.

This was intended (§5.2), and it is harmless: only Baton Pass reads the high nibble. But "a pack without handoff behaves exactly as before" is not byte-exact for the client's plan. The policy side is unchanged, as the FR/LG no-slot-write test shows.

**L7. The generator's proof covers only part of the hand-off function body.**

- **FR/LG** (`tools/gen_gen3_write_checkpoint.py:782-787`). The proof checks only that two pool words appear somewhere in the function body. It does not check the store or the exec-clear instructions.
- **RR** (`:769-777`). The proof checks the prefix at `+0x00..+0x0F`, the pool at `+0x40..+0x47`, and the CFRU LDR value. It does not check the detour word at `+0x48` (`0x0904459B`) or the hook body. `rr_active_faint.py` has no fact for the hook either; I checked the hook by disassembly instead (see "What I ran").
- **Consequence.** The claim "fail closed" holds only for the sha1-pinned dumps. The runtime permit never re-reads these bytes, because the anchors do not cover `PlayerBufferExecCompleted`.
- **Fix.** Add the hook as an `rr_active_faint.py` fact, and add an FR/LG `+0x00..+0x10` byte compare.

## Answers to the review questions

### 1. Safety

**Q: Can any plan other than exactly P+H get through `battle_commit_handoff`?**
Yes, but none of these plans is reachable from the client today:
- a consistent plan for battler 1, 2 or 3 (M1);
- a tail with any head, including `explode_plan() + hand-off` and `[comm, hand-off]` alone (L1);
- a plan that writes the slot through an IWRAM mirror (L2).

These are refused:
- the slot written twice;
- a byte written into the slot;
- the hand-off before the comm write;
- a wrong value, an even value, or a wrong slot;
- a tail for a different battler than `args.battler`;
- a malformed `handoff` block.

**Q: Does `write_plan`'s validate-once open a TOCTOU window?**
No. All five writes happen in one synchronous Lua call, and emulation is paused for that whole call, so no frame boundary or CPU step falls between the bytes.
- The per-write check never protected against the game running between writes, because the game cannot. It only protected against the plan invalidating itself.
- `write_plan` keeps the frame-equality check and the `allow` check for every entry, both done before the first byte.
- It re-runs the policy once, immediately before the first byte, with no reads or callbacks after that.
- It is bound by identity to the plan the window was armed with (`window.args.plan == plan`), and the policy already judged that plan both in `armed_write` and in `arm`.
- An entry outside `allow` throws before any byte is written, so there is no partial write.

**Q: Is the "slot must be the word the controller clause checks" guard real?**
For battler 0, yes: `h.address == ctrl.address + ctrl.offset`. For battlers 1-3 it is not (M1).

### 2. Order and addresses

**Plan rows.** The plan writes, in order: status3 `| 0x20`, timer `& 0xF0`, action `13`, comm `3`, then the hand-off. The clause enforces comm then hand-off as the last two entries.
- **Order does not matter to the game.** The plan is atomic with respect to the CPU, so the order of the rows is a policy convention only. What the engine needs is the comm value: 3, not 1.
- **Timer high nibble is kept** (`client.lua:721`).

**FR/LG addresses.** I checked each against `data/gen3/pret/*.sym` and pret:

### 3. FR/LG parity

**What `PlayerBufferExecCompleted` does.** In `src/battle_controller_player.c:186-200` it sets the slot to `PlayerBufferRunCommand`. In a link battle it transfers a buffer; otherwise it clears exec bit `gActiveBattler`. `BattleMainCB1` (`battle_main.c:2204-2209`) runs `gBattleMainFunc` first, then calls each slot with `gActiveBattler = i`, so the hand-off runs as battler 0.

**What happens next.**
1. HTAS case 3 (`battle_main.c:3350-3362`) waits for the exec bit to clear.
2. It then emits `LINK_STANDBY_MSG`, marks battler 0 for execution, and moves comm to 4.
3. `PlayerBufferRunCommand` dispatches `PlayerHandleLinkStandbyMsg` (`:2840-2856`). That handler runs `EndBounceEffect` twice and then `ExecCompleted`, the same sequence an A press produces.
4. The press path's `EmitTwoReturnValues` goes to buffer B, which state 3 never reads. The only things the hand-off skips are `PlaySE` and that ignored emit.

**Softlock.** I found no path that leaves battler 0 with a controller that never re-arms. `RunCommand` always re-arms on `MarkBattlerForControllerExec`. Link battles are excluded by `battle_not_link`. The Oak/Old-Man, Pokédude and Safari controllers use a different `HandleInputChooseAction`, so `battle_input_controller` refuses them. If a frame ends inside `HandleInputChooseAction`, it can only complete a press, and the result is equivalent. The RR L sub-UI case falls back to "press to continue", which is signed limit 17.

### 4. Unchanged behaviour

**Explode:** unchanged on all titles (L5). **Packs with no `handoff`:** the policy behaves as before. A slot-writing plan is now refused on FR/LG, which is a tightening. The client differs only in the timer nibble (L6).

### 5. Carrier oracles

**Is the proof engine-based?** Yes, not vacuous. The oracles read the engine directly:
- the controller slot and the exec flags;
- `gMain.heldKeysRaw` (`+0x28`, pret `main.h:29`);
- `gStatuses3`;
- `gBattleMons[0].hp` and PP;
- `gBattleResults` (`+0x00` and `+0x22`, `battle.h:337/353`);
- a faint-site callback that reads `gActiveBattler`, both HP words and the counter.

None of them uses the client's RESULT. The one client value used is `e.why`, as an extra check on top of the engine reads.

**Does it tell a Perish KO from a foe KO?** Yes. The Perish flag must be cleared at the KO frame, and the Perish script is what clears it; a foe's KO leaves it set. The oracle also requires no SLink HP write and the counter to rise by 1.

**Sample timing.** The hand-off check within 2 frames with exec bit 0 clear is deterministic whether the client writes mid-frame or at frame end. In both cases `ExecCompleted` clears the bit within the same frame.

**Presses.** The press counter wraps `joypad.set` before any helper loads, and `heldKeysRaw` is a second, independent check that covers every frame from observer install to the KO.

**SKIP.** Exit 3 is never treated as a success: `tests/e2e/test_duo_gen3.py` asserts `returncode == 0`, and `exit_code` returns 1 whenever any scenario FAILs.

**Weak spots:** the literal receipt fields (L3) and the watcher that throws silently (L4).

### 6. Generators and re-pins

**Fail-closed:** yes for the bytes the generator checks, which the mutation tests cover (4 RR bytes, 2 FR/LG pool words). The coverage is partial (L7). **Re-pins:** consistent everywhere in code; only docstrings are stale (L8). In `82f707c3`, only the sha1 citations change.
