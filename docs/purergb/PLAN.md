## 12. Executive summary — what we are building and how (2026-09-17, after the research phase)

**What.** pureRGB (three titles: PureRed, PureBlue, PureGreen; one pinned release, v2.7.6 = commit `7e7a4653`) becomes a second Gen 1 *foundation* on the Soul Link platform, `game_id gen1_purergb`, beside vanilla R/B/Y. Same rules, same client code, same server machinery; every game fact is regenerated from pureRGB's own source and canonical build. The companion features (native trade + START-menu panel) are rebuilt as a **source overlay** linked into the pureRGB build, shipped as a UPS over the pure ROM. Randomized pairs come from a **UPR ZX fork** with pure INI entries and a lossless handler.

**Foundations already in hand (facts, not assumptions).**
- The canonical build is reproducible: RGBDS 1.0.3 + w64devkit 2.10.0 → byte-identical to the release ROMs (§1); full `.sym`/`.map` captured; ROM0 has 1382 free bytes, banks `$3E/$3F` are empty, WRAM0 is full, the WRAMX bank-1 tail has 22 free bytes, HRAM is full (§3.1).
- Every hook site the client needs was resolved in the built ROMs and byte-verified (S1: 37/40 as predicted, 3 corrected), and the load-bearing ones were seen firing live in BizHawk (wild battle, trainer battle loop, faint, `EndOfBattle` in bank `$3A`, save witness) — with three same-address false hits in other banks proving the bank check is mandatory (§11.2 Live 2/3, S1).
- The overworld write checkpoint is `PC == $0040, [SP] == DelayFrame+24, [SP+2] == OverworldLoop+1, wDelayFrameBank == 0, WRAM BANK == 1`, measured on ~9,300 halted VBlanks at 2× speed; the flat `WRAM` domain equals bus bank 1; the GBC-fade bank-2 window never overlapped a VBlank in 243 warps (§11.2 Live 1/3).
- The vanilla scripted harness runs unmodified on pureRGB through the whole lab route and into Route 1 once two constants change (rival id 221, Oak-delivery script indices) — M2-e is a small per-foundation facts module, not a new harness (§11.2 Live 2/3).
- Data facts are census-complete: 248 maps / 69 areas with ROM-verified wild tables (W1), 190 species with 13 non-dex records and a 35-byte stride (A13), 56 trainer classes at offset 197 (A12), items/balls/bag (A6), charmap and text ABI (A10), options and flag gates (O3), NPC trades/daycare/cable club (A7), PC/save (A4).
- The UPR fork's INI is drafted with every key resolved and byte-verified (S2+W2) and the three handler patches are known (map-name stride 5, hidden-item entry set, 56 classes) — plus the lossless baseline C1 requires.
- The shared-server change (acknowledged `key_change`) has a complete reference census (O2) and its ordering fix is a move of one block in `server.py`.

### 2.2 How the server knows what happens (mechanism)

- **No ROM patch is required for the rules**; the companion patch only adds native trade/panel (`W/patch/gen1/README.md`; `W/docs/gen1_engine_sites.md:107-111` explains sites must avoid patched spans).
- **Writes**: force-faint = HP `0000` (+status 0) written to the party slot at the overworld checkpoint (halted CPU: `PC==$0040`, `[SP]==DelayFrame+5`, `[SP+2]∈{OverworldLoop+3, OverworldLoopLessDelay+3}`, WRAM predicates) — `W/lua/gen1_write_safety.lua:38-66`; active battler = `wBattleMonHP:=0`, `wPlayerSelectedMove:=$FF` at `MainInBattleLoop+0` under guards — `W/lua/gen1/writes.lua:25-35,62-76`, `client.lua:588-616`. - **Canonical state is the server's** (`links.json`); the client is stateless apart from latches; the server corrects the game (commands), not the other way round.

### 2.4 Lifecycle

- **New game / CONTINUE**: hello only at the overworld checkpoint or in a running battle; `Init` zero-fills WRAM so the main menu is not "in the game" (`W/lua/gen1/client.lua:168-173,871-874`; `W/docs/gen1_engine_sites.md:419-426`).
- **Save**: witness = `SaveMenu.save+3` (after `call SaveGameData`), then SaveRAM flush (`engine_signals.json save_witness`; `client.lua:529-530`).
- **Soft reset / reload**: latches cleared at `Init+0`; ROM re-verified (`W/docs/gen1_engine_sites.md:304`).
- **Disconnect / reconnect**: client drops events while disconnected (nothing buffered); every TCP edge sends `hello`; server treats each hello as a session start, re-derives faints from `hp==0` party entries, re-queues `memorialize`, `resolved_areas`, `config`, rebuild re-arm (`W/docs/protocol.md:66-127`; `W/server/state.py:927-1174`). Identity lock by OT id → `[x] WRONG SAVE` on mismatch (`state.py:943-969`).
- **Server restart**: links/areas/pending/memorials/identity/rom_type reload from `links.json`; memory-only partner queue is lost — recovered only if the partner's next hello shows `hp==0` (`W/server/state.py:125,786-909`).
- **Save rollback**: a wrong-save hello is rejected by OT; a same-OT rollback is only **partially** reconciled by the hello rules (re-quarantine, `hp==0` faint discovery, re-memorialize: `state.py:1020-1084`) — missing living members are not treated as dead and box-wide history is not compared; a complete rollback recovery is not claimed by the foundation.

## 5. Architecture decision (answers to the brief)

- **Interaction model** (unchanged): emulator memory reads at engine hooks + direct RAM writes at checkpoints; no runtime save parsing; ROM modification only for optional native UI/trade; TCP newline-JSON; canonical state on the server; recovery by hello re-sync (§2).
- **Can pureRGB be supported with an adapter/profile?** Yes for every rule the vanilla contract covers (encounter/dead zone/faint/party-PC/memorial/whiteout/evolution): the symbol-name contract holds (§3.2), struct sizes hold, every hooked routine exists; what changes is data (addresses, anchors, species/dex/types/areas/statics/trainers/items/moves/charmap) plus the (c)-class items in §4. **Conditional:** the pureRGB-specific identity rules (APEX, script transformations) depend on the two new gated write windows in §5.2 (`apex_commit`, `transform` HP restore) or on the recorded fallback policy; that feasibility is asserted only after their gates pass.
- **Does it need a compatibility patch?** Not for the vanilla-equivalent rules (the identity gates are client-side write windows, not ROM changes). For native trade/panel the vanilla binary patch does not transfer (§3.1, §3.5); the owner chose a **source overlay** built with pureRGB, which also hosts the ROM-side colliding-APEX refusal.
- **Port hooks into pureRGB / make pureRGB the foundation?** No. Observation hooks stay outside the ROM (bus-exec). The companion is an overlay applied at build time to a pinned checkout — never upstreamed and never a replacement for vanilla. Vanilla R/B/Y remains the product contract; pureRGB is an additional game (`gen1_purergb`) sharing the Gen 1 Lua client, codec and server machinery.
- **Shape**: `Gen1PureRGBAdapter(Gen1Adapter)` with `game_id = "gen1_purergb"` and its own `data/games/gen1_purergb/`; the Lua client stays one code base parametrised by the generated profile; generators gain a "foundation" (pret vs pureRGB) with a per-foundation source lock and assert set; the RC's generator standard (source-text + byte-shape asserts) is ported into the master lane for both foundations.
- **Maintenance**: one pinned pureRGB release at a time; a release bump = re-run the canonical build + generators, review assert failures, rebase the overlay, re-run gates (§7).

### 5.2 Review amendments (owner resolutions, 2026-09-16; reviewer exchange cx-1666864a rounds 1-2)

Status legend: FACT = source-backed; GATE = mechanism that stays unproven until its live gate passes; DECISION = user choice, recorded open.

**A1 - APEX CHIP contract (replaces "HUD warning").** FACT: the DV write happens inside the item routine before any observer can react (`P:engine/items/item_effects.asm#L1664-L1679`); the client re-keys before sending (`W/lua/gen1/client.lua:569-575`); the server migrates with no ack/rollback (`W/server/state.py:2465-2554`); a colliding key silently breaks faint propagation (`state.py:1707-1711`). Collision odds today are not exactly 1/65536 per same-species/same-OT pair (Gen 1 DVs come from two `Random` bytes, not a uniform independent word); APEX makes a collision certain only when both mons share OT id and species and both received a chip.
- Sites (corrected 2026-09-17 from the built ROM: the routine is `ItemUseMedicine.useApexChip 03:5B34`): `apex_preflight` = `.useApexChip+$0F` (= `.setDVs 03:5B43`; point: HL = the party mon struct, target slot = `wUsedItemOnWhichPokemon` — `wWhichPokemon` is restored to its pre-menu value at `item_effects.asm:1026-1028`; species/OT/DV snapshot) and `apex_commit` = `+$11` (both DV bytes written; `call .recalculateStats` follows at `+$13`; point slot + new DV word). The game itself no-ops an already-`$FFFF` mon (`#L1668-L1673 .alreadyUsedApex`).
- Client (GATE): at preflight compute the would-be key `FFFF:OTID:SS` for the slot; collision set = `known_keys` minus the mon's own old key (party + the latest scan of all 12 boxes, Box 12 included; the scan is refreshed on every PC/`move_mon`/`remove_pokemon` site and at start) plus pending-capture keys the server seeded; a hit is a predicted collision -> at commit, after re-checking the slot snapshot (species/OT unchanged), write the two original DV bytes back before `call .recalculateStats` (`#L1679`) runs. This is a **new armed window** (`apex_commit`) beside the five that exist today (§2.1); the **mechanism is proven live** (2026-09-17, §11.2 Live 4: a bus write inside the synchronous `on_bus_exec` callback at `ItemUseMedicine.useApexChip+$11` restored the old DVs after the game had written `$FFFF`, `.recalculateStats` then ran on the restored DVs, stats/HP/DVs were unchanged afterwards and the chip was consumed); what remains for T3 is the client-side collision prediction and the model replay, not the write window itself. If that gate fails, the decided fallback (U7) is to disallow APEX for pureRGB runs — last resort only, because the owner wants APEX working. Non-colliding APEX -> `key_change{old_key,new_key,reason:"apex_chip"}`, old->new kept as an alias until acknowledged.
- Server (shared protocol addition, detailed by the O2 census in §11.2): `_handle_key_change` becomes validate → (accept | reject) → mutate; the preflight refuses a **load-bearing** hit only — a different ALIVE `_key_index` entry, or the key present in any live structure (`party_keys`, `mon_stats`, `pending_captures`, `bonus_keys`, `pending_bonus`, `partner_blobs`, `rebuild_pending`, `pending_trade`, `queued_commands`/`sync_inflight`, and server-side `pc_boxes` outside the memorial box/`party_details`; **implemented 2026-09-18 without `mon_stats`/`_mon_cache`** — both are never-pruned caches holding every buried key, so counting them would make a buried key permanently unreusable, contradicting the rule below; pinned by tests) — while a DEAD/MEMORIAL index hit is accepted with the existing `KEY COLLISION` log (`_index_entry`), because a buried key is by design reusable (`test_gen1_identity_and_collisions.py:87-90`); the idempotent replay (`_key_index.get(new_key) is entry`) and an unknown `old_key` (Gen 3 nature change on an unlinked mon) both **ack** (`migrated:false` for the latter); the reply line carries `key_change_ack{old_key,new_key}` or `key_change_rejected{old_key,new_key,reason}` (Gen 3 ignores unknown commands, `W/docs/protocol.md` §1.2). Cross-player collisions (same OT id on both cartridges) are only catchable here, never by preflight. Rejection is the fail-closed backstop; its consequence is decided (U5): the old key's link -> DEAD `cause=identity_lost`, partner force-fainted, both memorialized. Consumed chip on a rules-only refusal: decided (U6) as accept-and-document, with the overlay build refusing a colliding use before consumption (see the decisions paragraph below).

**A2 - Transformation never revives.** FACT: `ChangePartyPokemonSpecies` recalculates stats and sets current HP := new max HP (`P:engine/pokemon/change_mon_species.asm#L34-L49`); the scripts only check species (`P:scripts/CinnabarVolcanoWest.asm#L41-L47`), so a fainted or canonically dead mon can be transformed and come back at full HP. Contract: at the `transform` site the client records `(slot, old_key, old_hp)`; after settle it sends `key_change{reason:"transform"}` (acked as A1); if `old_hp == 0` the HP must be forced back to 0 before the mon can act. Two mechanisms, both GATE: (i) in-routine restore right after the HP store (`#L46-L49`, same class of window as the APEX commit write), preferred if the A1 window proves; (ii) re-zero at the next overworld checkpoint, acceptable only with a measured bound (gate: frames between `transform` and the re-zero, and no `battle_begin` in between). Server: if the old key's link is DEAD/MEMORIAL it re-queues `force_faint{new_key}` + `memorialize{new_key}` (pending memorials already migrate, `state.py:2465-2554`).

**A3 - Artifact admission contract.** Kinds per title: `clean` (pinned release), `overlay` (SLink build), `rand` (UPR over clean), `rand_overlay` (UPR over overlay). Admission is always a **full-ROM sha1**: pinned set for `clean`/`overlay` (profile `admission: {sha1 -> {title, kind, profile_id}}`); for randomized artifacts the preparation contract must bind the final output sha1 plus provenance (`foundation`, `title`, `kind`, `profile_id`, UPR fork version, settings hash) and the server compares the hello `rom_sha1` to it in addition to the table fingerprint (today `rom_contract.json` stores `rom_sha1` but `_decide_admission` never reads it: `W/server/manager.py:958-960` vs `W/server/server.py:508-545`); the "no contract => admitted" default (`server.py:514-515`) is narrowed to pinned sha1s. Header title only names the candidate profile list (for `POKEMON RED`/`BLUE` that list includes the vanilla profile because the titles collide); the client then verifies the **full** site + checkpoint anchor set of the selected profile as a runtime integrity check, never as the admission proof; clean and overlay profiles must each pin at least one anchor that differs from the other (the hook sites) so candidates cannot mis-select. `rom_type` stays per title; overlay capability is detected from the overlay `.sym` hook bytes, not `0x29C3`.
