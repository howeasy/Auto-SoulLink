## What is proved, and what is not

Evidence levels are distinct: **source/ROM** (pinned pret, clean and companion bytes), **unit/model**, **controlled original engine**, **checked downloaded launcher**, **real paired Manager/gameplay**, **human play**. A result at one level never silently promotes to the next. Registration in the release manifest means a reviewed executable proof is named, not that it passed on current source. Peer agreement, held startup, synthetic fixture, and a queued message are not gameplay or recovery receipts.

Integrated on main: canonical R/B/Y data and admission, shared journal/session/client primitives, quiet 1×/3× free-service baseline, service lease and continuity, HUD component behavior, source-backed R/B/Y memory boundaries, in-battle instruction liveness correction, and non-live source/Manager corrections. Their component evidence is valuable but has not produced a complete current-source release verdict. Main still has no production native trade or full playthrough approval.

**RC finish line:** the final frozen build's `automation.json` must report `automation_passed: true` from the non-quick [release runner](../../tools/verify_gen1_release.py), with all **387 non-human** requirements covered by its 15 checks and eight pinned prerequisites, no skip/xfail/deselection or input drift. The 388th `human-session` row is deliberately outside `automation_passed`; `--complete-human` and the staged two-player attestation are the later **release** verdict. A successful automation run can still exit nonzero while human sign-off is pending, so read the report field, not the process exit code alone. This defines one RC target rather than silently moving between “feature-complete,” “playable,” and “released.”
