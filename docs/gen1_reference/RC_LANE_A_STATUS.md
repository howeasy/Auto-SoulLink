## Compressed WAL prototype decision record — 2026-09-13 00:45 UTC

External-change parity is a hard precondition, not a later optimization: current `state_store.commit` performs `backend.read()==wire` before each mutation. The WAL facade must retain the existing per-run/player `.lock` and hold its active `FileStream` with `FileShare.None`, **then still reread and compare the exact expected bytes** of its checked base, sealed segment (if any), and active segment before each commit. A tail-length or last-record check alone would miss mid-file corruption and is insufficient. After appending, exact data+marker readback must match the proposed bytes, revision and chain; any mismatch latches and holds. Reopen revalidates every authoritative byte, full decompression/canonicalization and the complete client journal. The near-full two-segment reread/hash cost belongs in the performance bound; the lock prevents ordinary competing file owners but is not used to excuse adversarial in-place mutation.

Generation/migration crash ordering to prove: while upgrading an existing journal, the fully checked legacy file remains authoritative until a new base, WAL header and selector candidate have each been flushed/read back, and an atomic selector switch succeeds. Crash before selector switch reopens legacy; after it reopens WAL; invalid selector or contradictory generations hold, never guess. During compaction, seal the old log, open and read back a new segment anchored to the old tail, then build a new immutable base from a checked revision without blocking the frame thread. Until the atomic generation selector points at the new base, old base+segments remain authoritative; after selector readback, new base+suffix log are authoritative and old files may be retired only by the verified owner. Crash at every boundary must select one complete chain or hold, never mix a newer base with a stale/missing suffix. Active commits must continue against the selected segment while background work runs; if the two-segment bound would overflow before switch, hold/fail closed rather than silently grow or block an unbounded number of 3× frames.

Authority/recovery invariant: pre-send full observation bytes remain reconstructible from the marked local outbox before source drain or another emulated frame; an ACK containing commands is marked and read back with the inbox before any executor step. Crash before the data flush, between data and marker flushes, after marker before send, after server commit before local ACK marker, and after ACK marker before execution must respectively recover the last valid prefix or replay the exact persisted operation without lost/duplicate physical effects. A **valid marker with bad data/hash/chain always refuses**. An incomplete final unmarked tail may be discarded only under the program-order rule that no send/execute occurs before marker readback; adversarial truncation of a previously committed marker is indistinguishable from cross-restart rollback without an external high-water anchor, a limitation already present for rollback to an older valid `state_store` file. Within one process, exact prior base/log bytes and expected revision must be rechecked before every commit and any mutation latches the store. If the release threat model requires detecting such cross-restart truncation, recovery must hold for server-anchored reconciliation instead of silently discarding; that is an unresolved owner decision. Reopen fully scans, decompresses with bounds, re-encodes for canonical-byte equality, checks binding/chain and invokes the unchanged client-journal validator; never accept a merely parsable corrupt source.

Growth/compaction invariant: battle may emit a null-inventory observation every 30 frames (~6/player/s at 3×). Full-state compressed log records plus ACKs could grow by roughly `1–2 KiB` per heartbeat (~`20–40 MiB`/hour/player), so an unbounded log or a one-time bedroom pass is disallowed. Bound segments (candidate `256 KiB`) and use a sealed old segment plus a new active segment anchored to its digest while an immutable checked base is compacted. Publish a new base with atomic flushed replace/readback **before** switching the generation manifest; retain old base/segment until that switch is durable, and validate all crash points. Do not run compaction on the frame thread during active gameplay. Limit to two segments; if background compaction cannot keep up, hold/fail closed before growth exceeds the cap. Every commit must freshly check the bounded authoritative base/log bytes to retain external mutation detection; measure that read/hash cost at a near-full segment, not only an empty-log microbench.
