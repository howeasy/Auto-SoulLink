## 1. Whiteout (server side)

`server/gen1_whiteout.py`:

* `whiteout_from_faint(previous_inventory, current_inventory, faint_signal, *, area_id)` returns
  `whiteout_event(area_id=...)` (`server/gen1_semantic_events.py`) when no party HP is left after this faint,
  mirroring `AnyPartyAlive` (`.cache/pret/pokered/engine/battle/core.asm:1455-1470`): the HP of every slot of
  `point.party_hex` (slot `s` at bytes `9+44s..10+44s`, big-endian) ORed together once the fainting slot carries
  its truth: `battle_hp` for `battle_faint` (the hook fires at `RemoveFaintedPlayerMon+0`, before the copy-down at
  `core.asm:1023`, so the active slot may still show stale HP), the slot named by `which` for `poison_faint`
  (validated at zero already). `previous_inventory` and `current_inventory` are accepted for the P5 section 3
  contract and unused: corroboration only, never the trigger.
* `area_for_map(map_id)`: `point.map_id` through the adapter area map (`_MAP_ID_TO_AREA` in
  `server/adapters/gen1_rby.py`), None for an unmapped map as the acquisition and wild-encounter runtimes do.
  `_handle_whiteout` never reads it; it is dashboard context.
* `settle_whiteout(stage, document, player, entry, index, signal)`: called by `gen1_faint_runtime.settle` right
  after each settled faint (P5 section 5 ordering: the fainted pair is already DEAD, so `_handle_whiteout` cannot
  queue a second peer death for it). It hands the event to `stage.rules.handle_event`, refuses with `JournalError`
  if the engine queued any `force_faint`/`force_explode` (a linked party member the faint settlement left alive,
  unreachable under the ordering rule), drains the rest of the queue exactly as P8 drains after the faint
  (memorialize, hud_show, game_over and the party_mon of a rebuild are decided here and executed elsewhere or not
  at all until the item-4 executor map), and records once.
* The record lives in a new component `gen1-whiteout-settlement`, keyed by the death identifier
  (`identifier(player, operation, index)`): `{player, engine_record, index, area_id}`.
  `gen1_faint_runtime.verify_state` pins `gen1-faint-settlement` to exactly `{activations, deaths}`, so a
  `whiteouts` key there would have broken it; the separate component leaves that check untouched.
  `gen1_whiteout.verify_state(stage)` recomputes every record from its engine evidence (`verified_source`, the
  same identifier, the same event, and a death of the same identifier must exist). It is not yet called from
  `server/gen1_runtime_state.py` (not a P12 file): two lines next to `verify_faints`.

Under the RC every faint is settled individually before the detector runs, so the whiteout finds no ALIVE link in
the party; its effects are `party_keys[player].clear()`, the rebuild plan when boxed alive pairs exist, and
`_check_game_over`. The existing fixture faint (a one-member party at HP 0) is already whiteout-shaped, so the
faint, deferred-faint, memorial and held-faint suites exercise the wiring.

## 2. Rival team executor

### Addresses (`data/games/gen1_rby/rival_team_checkpoint.json`, generated by `tools/gen_gen1_rival_team_checkpoint.py`)

| Symbol | R/B | Yellow | Source |
| --- | --- | --- | --- |
| `wIsInBattle` | `D057` | `D056` | `data/pret_syms.json` (pokered / pokeyellow); equals `BATTLE_FLAG_ADDR` in `lua/games/gen1_rby.lua` |
| `wEnemyMonPartyPos` | `CFE8` | `CFE7` | `data/pret_syms.json` |
| `wEnemyPartyCount` | `D89C` | `D89B` | `data/pret_syms.json`; equals `ENEMY_COUNT_ADDR` |
| `wCurOpponent` | `D059` | `D058` | `data/pret_syms.json`; equals `CUR_OPPONENT_ADDR` |
| `wLinkState` | `D12B` | `D12A` | `data/pret_syms.json`; equals `write_safe.link_state` |
| `wBattleType` | `D05A` | `D059` | `data/pret_syms.json` |
| `irq_vector` / `vblank_entry` / `delay_frame` / `vblank_flag` | `0040` / `2024` / `20AF` / `FFD6` | `0040` / `1DE5` / `1E64` / `FFD6` | `lua/games/gen1_rby.lua` `write_safe` (the bytes `write_checkpoint.json` already exports) |
| stack window | `DF00..DFFF` | `DF15..DFFF` | same |

The generator asserts that the pret symbols equal the client profile names it reuses, writes the JSON for the
server and the Lua twin for the client, and `--check` fails when either is stale
(`test_checkpoint_data_artifacts_match_their_generator`). The footprint written is unchanged from P5 section 3:
`67n + 2` bytes over `wEnemyMons`, `wEnemyMonOT`, `wEnemyMonNicks`, `wEnemyPartySpecies`, `wEnemyPartyCount`.

### Checkpoint predicate `battle_init` (`M.check` in the Lua == `verify_battle_init_checkpoint` on the server)

ROM anchors: `irq_vector` holds `JP vblank_entry` and `delay_frame` the eight bytes of `DelayFrame`. CPU:
`pc == irq_vector`, `stack_min <= sp <= stack_end - 1`, the resume word at `[sp]` is `delay_frame + 5` (halted in
`DelayFrame`; the caller word is not pinned, the intro has many), `vblank_flag == 1`. Bytes: `wIsInBattle == 2`,
`wEnemyMonPartyPos == 0xFF`, `wEnemyPartyCount in 1..6`, `wCurOpponent == body.trainer_id` (201..255 in the Lua;
a rival id 225/242/243 on the server), `wLinkState == 0`, `wBattleType == 0`. Why it is safe: `InitBattleCommon`
sets `wEnemyMonPartyPos = $FF` and `wIsInBattle = 2` right after `ReadTrainer` filled the party
(`core.asm:6679-6692`; Yellow `engine/battle/init_battle.asm:39-51`), the value survives until the first send-out
writes it (`core.asm:1720`), and `StartBattle` scans and sends out with no `DelayFrame` between
(`core.asm:139-156`), so every VBlank boundary satisfying the predicate lies strictly inside the window.

### Executor and verifier

* `lua/gen1_held_rival_team.lua`: `handles`, `check`, `capture` (exactly the reads of `check`, the
  `gen1_write_checkpoint` shape) and `new(o)` with `prepare` (the client blob rule of
  `gen1_rby_client.lua:340-355`, `Codec.validateParty`, at least one living member because the `StartBattle` scan
  has no exit), then `classify`/`apply`/`receipt` over the image: the `67n+2` bytes `M.writeEnemyParty` writes, in
  write order (per mon struct, OT, nick, species byte; then `FF` and the count). `apply` is `M.writeEnemyParty`.
  Receipt `gen1-rival-team-receipt-v1 {trainer_id, before, after}`, `after = {count, species_list, image_hex}`;
  the full readback stands in for a digest because the server compares it byte for byte.
* `lua/gen1_held_faint.lua` (patch): requires the module, `handles` accepts the command, `selected` dispatches to
  it, `safe()` uses the battle_init predicate while the pending command is the rival swap, and `request` uses its
  evidence schema `rby-held-rival-evidence-v1`, its checkpoint and its image. Permit, phases and flow unchanged.
* `server/gen1_held_rival_team.py`: `verify(player, command, evidence, state, binding)` mirrors
  `gen1_held_faint.verify` (`verify_owned_host`, the battle_init checkpoint, the intent
  `rby-rival-team-intent-v1 {trainer_id, n, before}`, `current` equal to `before` or the expected image) and returns
  `VerifiedHeldWrite(command_scope(..., phase="replace_rival_team"), ...)`; `verify_rival_team_receipt` rebuilds
  the expected image from `blobs_hex` and checks the count and `[blob[0] ...] + [255]`. Not yet dispatched from
  `gen1_held_faint.verify` (not a P12 file): one `cmd == "replace_rival_team"` line; `Gen1ReceiptPolicy` still
  accepts only `force_faint`.
