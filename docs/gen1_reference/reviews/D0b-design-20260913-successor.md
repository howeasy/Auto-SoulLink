## Question

Can a normally saved, cleanly exited selected run gain fresh physical ownership and resume its existing logical run while retaining identity, rollback, pending-write and native-trade refusals? **Answer today: no, by construction, at four independent gates (section 2).** The gates are deliberate; the identity registry already carries the one seam a new lineage needs (section 4). The rest is unspecified and listed below as hypotheses and owner questions.

### 1b. Sequence: ordinary save → exit → bundle relaunch → HELLO → held observation → authority decision

1. **Ordinary save (PRET).** `SaveMenu` → `SaveGameData` sets `wSaveFileStatus=2` and copies exactly `sPlayerName/sMainData/sSpriteData/sCurBoxData/sPartyData/sTileAnimations` then `sMainDataCheckSum` (`.cache/pret/pokered/engine/menus/save.asm:150-296`). `server/gen1_full_save.image()` (`:42-55`) models that transform from a held WRAM point; the client's `gen1_full_save.lua:49-62` is the same function. **SLink observes nothing at this moment**: `data/games/gen1_rby/engine_signals.json` hooks only `bag_received, battle_faint, poison_faint, starter_begin, starter_end`; the heartbeat batch that follows carries the new SRAM bytes inside `cart_hex` but the server never compares them to the WRAM image.
2. **Clean exit.** The client `close()` (`gen1_client_entry.lua:600-618`) sets the lifecycle hold, revokes the runtime and closes the store; it neither flushes SaveRAM nor records anything. BizHawk writes `game.sav` on ROM close (unwitnessed, inferred from EmuHawk behaviour, not from SLink source). The server sees a disconnect → `disconnect()` → `suspend()` (`durable_runtime.py:443-447,426-441`): service epoch rotated, `_service_recovery_required=True`, hold notice to the peer, trades interrupted (`gen1_runtime.py:353-356`), sessions cleared.
3. **Bundle relaunch.** `tools/launch_bizhawk.py` → `bizhawk_launch.prepare` reuses the same `<root>/<run_id>/<player>/{emulator,SaveRAM}` only if `launch.json` is byte-identical (`:87-93`), so the same private `.sav` and the same client `journal.json` (path `gen1_client_entry.lua:123-133`, root from `SLINK_CLIENT_STORAGE_ROOT` set at `bizhawk_launch.py:107`) are reused. Nothing here talks to the server: **owned SaveRAM preparation grants no re-enrollment** (confirmed).
4. **Script start.** `M.start` mints **two fresh nonces** (`:73-74`); `Store.open` accepts the existing journal because its binding is `{run_id, player, cartridge, save_identity}` only (`lua/state_store.lua:38-73`), so the relaunched client believes enrollment is `acknowledged` and inherits `observation_cursor`/`pending_inventory_retry`/pending outbox. `begin()` runs at the first visible party-write-safe frame (`:486-511`, Yellow/native: after the boot frame(s) `:492-508`).
5. **HELLO.** `lua/gen1_runtime.lua:14-28` reports the new nonces; `durable_runtime._admit:152-180` and `gen1_runtime_state.admit:191-209` accept because only `save_identity` is compared; the admissions ledger now holds the **new** metadata/binding while `gen1-initial-observations` and `identities.contexts` still hold the **old** ones. `bind_context` is not called on HELLO. Barrier rebinds and invalidates (`paired_recovery.py:135-148`).
6. **Held observation.** Native launch: `classify_reattach` (`:546-567`) publishes the start-of-script read against the **current** admission (`gen1_native_reattach_runtime.py:150-156`) and a clean read is `released`. Ordinary launch: nothing is published; the client sits in `held_service` (`:470`).
7. **Authority decision.** Control turn: client `lua/durable_runtime.lua:464-466` asks `service_continuity(...)`; `gen1_client_entry.lua:287-288` answers `deferred("free observation loop is not initialized")` because `self.loop` is nil, and the loop is only built by `start_loop` after `loop_ready` → `has_service_lease()` (`:395-406`, `lua/durable_runtime.lua:535-545`) → server authority `service` → `_service_recovery_required=False` → both proofs (`durable_runtime.py:242-244`). **Circular by design: a restarted client never sends a proof.** Server reason stays `player a disconnected; paired reconciliation required` (`:446`) or, after a server restart, `runtime reopened after client evidence; service continuity recovery is required` (`:97-99`).

## 2. Present refusal path and the smallest executable reproduction

### 2a. The four gates, in the order a relaunched client meets them

1. **Client gate (FACT).** `gen1_client_entry.lua:287-288`: no loop → no proof. Observable as `status().continuity == {state="deferred", reason="free observation loop is not initialized"}` and `phase=="held_service"` forever.
2. **Continuity gate (FACT).** If a proof were sent: `gen1_service_continuity.verify:84-89` compares current admission metadata (minus `control_binding`) with `initial["metadata"]` and the binding's `context_generation` with the initial one → `service continuity admission differs from the initial physical identity`. Second refusal behind it: `:182-185` (`point["host"]` ≠ initial host; `point["frame"] < cursor["frame"]` after a frame-counter reset) → `service continuity host or frame changed`. Existing MODEL coverage bumps only `inventory.host.process_id` (`tests/unit/test_gen1_service_continuity.py:292`) and every test admits with the constant nonces of `tests/unit/test_gen1_initial_observation.py:31-36`; **no test presents a new admission context.**
3. **Observation gate (FACT).** Even with service authority, every batch is refused at `gen1_observation_runtime.py:121-125` (`context_generation` ≠ initial) and `:132-133` (`observation frame moved backwards`, since the relaunched emulator counts from 0 and the floor is the last committed frame).
4. **Write/window gates (FACT).** Held faint receipts need the initial instance **and initial PID** (`gen1_held_faint.py:96-104`); battle instruction windows are issued for the initial instance and anchored at the initial frame (`battle_force_authority.py:313-317`); durable native windows require current admission == enrolled host (`gen1_native_progress.py:55-68`). These are why "same PID or equal bytes alone is not rebind authority" already holds.

Plus one latent defect found on the way (**FACT by source, not observed**): a durable event left in the client outbox at exit is replayed after the next HELLO (`lua/durable_runtime.lua:486-497`). A replayed `observation` carries the old `physical_instance`, is refused at `gen1_observation_runtime.py:123` (compares to the **current** admission), the NACK revokes the session (`lua/client_session.lua:77-79`, `lua/durable_runtime.lua:308-309`), the client reconnects and replays the same event. There is no discard path, so a restart with a non-empty outbox loops forever. Any resume design must require an empty acknowledged outbox and must not add a discard.

## 3. Proposed definition: "acknowledged idle checkpoint" (DESIGN)

Vocabulary, extending [`CONTEXT.md`](../../../CONTEXT.md): an **inventory checkpoint** is a coherent WRAM observation at one held frame; an **idle checkpoint** is an inventory checkpoint whose SaveRAM projection is on disk and acknowledged; a **lineage** is one physical host `{context_generation, physical_instance, process_id}` bound to the immutable run identity.

**Hypothesis H1.** An idle checkpoint for player *p* exists when one journal commit records all of the following for the same frame *f*:

| Field | Producer | Persistence | Consumer | Tamper/rollback check |
| --- | --- | --- | --- | --- |
| `inventory` = the full-save point already captured by `gen1_inventory_checkpoint.lua` under the writer hold | client loop, existing | server `gen1-inventory-observations` (existing) | resume verifier | `image(point)` recomputed server-side from the pinned layout (`gen1_full_save.py`), never trusted from the client |
| `file` = `slink-saveram-file-v1` receipt from `platform_saveram.flush(expected_hex)` with `expected_hex = image(point)` (existing module: flushes via `MainForm.FlushSaveRAM`, reopens the file `Share.None`, reads back, hashes, asserts the frame did not move `:74-103`) | client, existing module, **new call site** | server, new component `gen1-idle-checkpoint[p]` = `{operation_id, sequence, frame, file_sha256, byte_length, inventory_digest, history_digest, binding_digest, context_generation}` | resume verifier; later release evidence | server `save_file_receipt.verify_file_image(receipt, image(point), host_profile, f, f)` (existing) proves file bytes == projection at frame *f*; a mismatch (unsaved progress since the last in-game save) is the refusal |
| `history_digest` = `stage.barrier.document()["history_digest"]` at commit (existing: `gen1_runtime_state.recovery_history` over rules/identities/trade) | server | same record | resume verifier | any later semantic mutation changes it |
| idle predicate = the existing `gen1_service_continuity` idle set (`:106-123`: no pending events/commands, no open acquisition/instruction/battle, no durable command, no non-terminal trade; native: released reattach, idle lease) | client loop `continuity()` + server checks, existing | evaluated at commit, recorded as the fact that the record exists | — | re-evaluated at resume |
| `acknowledged` = the client store's `observation_cursor.sequence == observation_sequence == checkpoint.sequence` (existing meaning of "durably acknowledged", `gen1_observation_loop.lua:155-166`) | client store | `journal.json` | client, before it will present the checkpoint | server side is authoritative (section 4) |

**Both-player synchronisation (H1, continued).** No new pairing field. The server already suspends both players on either disconnect, so each player's idle checkpoint is simply its own latest such record; resume requires **both** players' current records and that no semantic history committed after either (`history_digest` equality, section 4). Staggered exits are therefore allowed only when the second player also saved before the first player left (section 5).

**When to take it (H1a/H1b, one must be chosen).** (a) Only when the client is about to exit or the peer is held: needs a product "save and quit" affordance the client cannot provide because in-game saving is impossible under the lifecycle hold. (b) **Recommended:** opportunistically at every heartbeat where the player-write-safe projection equals SRAM (`image(point) == cart_hex`, a pure comparison, no flush) *and* the last idle record is older than that projection; then flush and publish. This captures every ordinary in-game save while the connection is live, with no new engine hook, no new prompt, and the flush is a no-op write when SRAM already equals the file. Cost: one extra 32 KiB file flush per in-game save.

**Not proposed:** a `SaveGameData` engine signal (`.cache/pret/pokered/engine/menus/save.asm:290`) is hookable and would make (b) exact, but the pure `image == cart_hex` comparison already detects the same fact one heartbeat later; add the hook only if the heartbeat lag is observed to matter.

## 4. Authoritative high-water, rollback domain, identity versus lineage

### 4a. Which state is authoritative (DESIGN, built on FACT)

| Store | Rollback domain | Role |
| --- | --- | --- |
| server `runtime.sqlite3` (`RuntimeLease` `.server.lock`, `gen1_runtime.py:144-145`) | the Manager host | **authoritative** for logical high-water: `gen1-observation-progress`, latest inventory, proposed idle checkpoint, `history_digest`, identities |
| client `journal.json` | `<root>/<run_id>/<player>/`, same directory as the SaveRAM | a cache of acknowledged cursors plus the durable outbox; must equal the server or HOLD (today `gen1_service_continuity.py:98-100` already refuses any cursor disagreement in either direction; keep that shape) |
| `game.sav` | same directory as `journal.json` | the **physical** high-water; presented at resume as the fresh boot's `cart_hex` |
| native lease store | same directory | must be `idle`/`released` (existing check `:124-146`) |

The client journal and the SaveRAM **share a rollback domain** (one directory, one user, one backup/restore), so agreement between them proves nothing about rollback; only the server record can detect a client-side rollback, and it does so by `sha256(cart_hex at boot) != checkpoint.file_sha256`. The server's own rollback (a restored `runtime.sqlite3`) is detected only if the client presents a cursor *ahead* of the server; the existing equality rule turns that into HOLD, which is the correct fail-closed outcome. Neither side can distinguish "older" from "newer unwitnessed" by hash alone; decoding the file (party/box semantics versus the checkpoint) is diagnostic text only, never authority.

### 4b. Immutable identity versus lineage (FACT + DESIGN)

- **Keep immutable:** `run_id`, the paired contract/cartridge digests, `save_identity`, the `gen1-initial-observations` record itself (it is the enrollment witness and the anchor of every historical receipt; `:165` "initial observation is immutable" stays true), logical member ids (resolved by `(player, save_ref, key)`, `identity_registry.py:288-291`, so members survive a new host).
- **Already lineage-capable:** `IdentityRegistry.bind_context` (`:123-142`) accepts a new `{context_generation, physical_instance}` for the same save, appends to `context_history`, forbids reusing a retired context (`:132-133`) and forbids sharing a physical instance with the peer (`:134-136`). Receipts already reference contexts by value and are validated against `context_history` (`:373,391`). **This is the seam; no new identity concept is needed.**
- **Not lineage-capable today:** every consumer in section 1a that reads `initial["metadata"]["gen1_metadata"]["physical_instance"]`, `initial["binding"]["context_generation"]`, `initial["observation"]["host"]["process_id"]` or `initial["observation"]["frame"]` as the *current* host. `gen1_native_progress.enrolled_host()` (`:18-26`) is the only place that already names this concept as a function.
- **DESIGN H2:** introduce one server accessor `current_host(document, player)` returning the newest accepted lineage entry `{context_generation, physical_instance, process_id, anchor_frame, binding_digest, ordinal}` (falling back to the initial record when no re-enrollment exists) and make the section-1a consumers read the host through it. The initial record is never rewritten.
- **Allowed to change at resume:** `admission_epoch`, `session_id`, `binding_digest`, `service_epoch`, `context_generation`, `physical_instance`, `process_id`, the recovery-barrier epoch; the **frame floor resets** to the re-enrollment observation's frame (a new `anchor_frame`), while `sequence` continues monotonically from the checkpoint (`observation_sequence` is already persisted client-side and enforced `+1` server-side `:130-131`). **Must not change:** anything in 4b's first bullet, the checkpoint's `inventory_digest`, `history_digest`.
