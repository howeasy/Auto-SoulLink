## 1. The save routine and its completion instruction (FACT, PRET + ROM bytes)

| Symbol | Bank:addr | Flat | Bytes read from the clean ROM | Meaning |
| --- | --- | --- | --- | --- |
| `SaveGameData::` | `1c:7b91` | `0x73B91` | `3E 02 EA 87 D0 CD E5 7A CD 32 7B C3 56 7B` | `ld a,2; ld [wSaveFileStatus=$D087],a; call SaveMainData; call SaveCurrentBoxData; jp SavePartyAndDexData` (`engine/menus/save.asm:274-279`) |
| `SavePartyAndDexData` | `1c:7b56` | `0x73B56` | `CD 9F 7E 3E 01 EA 00 40 …` | third copy: party, dex, Pikachu happiness, then checksum (`save.asm:248-272`) |
| tail of `SavePartyAndDexData` | `1c:7b8a` | `0x73B8A` | `EA 23 B5` `CD AA 7E` `C9` | `ld [sMainDataCheckSum=$B523],a; call DisableSRAM; ret` |
| **completion instruction** | **`1c:7b90`** | **`0x73B90`** | **`C9`** | the `ret` that ends `SavePartyAndDexData`; because `SaveGameData` tail-jumps, this `ret` returns to `SaveGameData`'s **caller** |

At PC `1c:7b90`, before the `ret` executes, **when reached through `SaveGameData`**: all three SRAM copies and the checksum are written, SRAM is disabled again (`DisableSRAM` `1c:7eaa`), `wSaveFileStatus == 2`, and `hLoadedROMBank` (`$FFB8`) is `0x1c`. Nothing after this instruction touches SRAM in the save path.

**[R2] What `1c:7b90` does and does not establish.** It establishes *routine completion*: `sMainDataCheckSum` equals the complement-sum of `sGameData` as written, and the three copies are complete. It does **not** establish that current WRAM equals SRAM. The copies are sequential (`SaveMainData` copies `wMainData` first, `save.asm:200-231`; party/dex last, `:248-272`), nothing in `save.asm` or `CopyData` (`home/copy.asm:13-23`) executes `di` or stops the timer, and `TrackPlayTime` runs from the VBlank handler (`home/vblank.asm:41`) incrementing `wPlayTimeFrames` (`00:da44`, inside `wMainData`) whenever `wStatusFlags6` `BIT_GAME_TIMER_COUNTING` is set (`home/play_time.asm:1-10`). A copy of ~7.5 KiB spans VBlanks, so at the `ret` the WRAM play-time bytes may already be ahead of `sMainData`. Whether the timer bit is set during `SaveMenu` is **unverified**; even if it were clear, equality would be a measured fact, not a construction. Revision 1's "holds by construction" is withdrawn.

## 2. Call and return paths (FACT)

`SaveGameData` has four callers in the pinned tree plus one in the same file, and **[R2]** `SavePartyAndDexData` has one direct caller of its own, so the `ret` at `1c:7b90` is reached by two different kinds of save:

| Caller | Site | Where the `ret` at `1c:7b90` returns | Path | Full save? |
| --- | --- | --- | --- | --- |
| `SaveMenu` (`1c:7a67`), START menu SAVE via `predef SaveMenu` (`engine/menus/start_sub_menus.asm:663`, `data/predef_pointers.asm:76`) | `call SaveGameData` at `1c:7a95` (`CD 91 7B`) | `1c:7a98` (`21 D6 7A`, `ld hl, SavingText`), in-bank | ordinary player save | yes |
| `ChangeBox::` (`1c:7bea`, `save.asm:342-386`) | `call SaveGameData` after swapping boxes through `CopyBoxToOrFromSRAM` | inside `ChangeBox`, in-bank | Bill's PC box change | yes |
| `engine/link/cable_club_npc.asm:70` | `callfar SaveGameData` | `Bankswitch` trampoline `00:3e84` (see below) | link entry quick-save | yes |
| `scripts/HallOfFame.asm:50` | `farcall SaveGameData` | `Bankswitch` trampoline | Hall of Fame | yes |
| `engine/debug/debug_menu.asm:1571` | `callfar SaveGameData` | `Bankswitch` trampoline | debug | yes |
| **[R2]** `engine/link/cable_club.asm:870` | `predef SavePartyAndDexData` ("this allows reset into Pokecenter") | `Predef` trampoline `00:3eb4` | after a completed Cable Club trade | **no**: party + dex + happiness + checksum only; no `SaveMainData`/`SaveCurrentBoxData`, `wSaveFileStatus` not set |

**[R2] Consequence:** a hook at `1c:7b90` fires for *partial* saves too. "Three copies written and `wSaveFileStatus == 2`" is true only with `SaveGameData` provenance, which the hook PC alone does not give; the entry `1c:7b91` (`SaveGameData::`) is the only in-ROM point that proves the full routine began, and pairing begin/end signals (or reading `wSaveFileStatus` at the `ret`, which `SaveGameData` sets to 2 before its copies while the partial path leaves it untouched) would be design, not fact.

**[R2] Return addresses:** `farcall`/`callfar` expand to `ld b,BANK; ld hl,target; call Bankswitch` (`macros/farcall.asm:8-18`), and `Bankswitch` (`home/bankswitch2.asm:6-18`, `00:3e84`) reaches the target through `call JumpToAddress` (`00:3e98`, `jp hl`), so every far caller's `ret` lands on the same trampoline return address; `predef` likewise returns into `Predef` (`home/predef.asm:1-15`, `00:3eb4`). Only the two in-bank `call`s (`SaveMenu`, `ChangeBox`) leave a caller-specific address on the stack. Revision 1's "distinct return address per caller" is withdrawn; classifying far callers would need the trampoline's saved state (`wPredefID`, the pushed bank), which is unverified here.

**Cancellation (FACT):** `SaveMenu` returns via `ret nz` at `1c:7a7b` (No to "Would you like to save?") and `1c:7a94` (No to "older file will be erased") — both before `call SaveGameData`; no SRAM write, `wSaveFileStatus` unchanged. `ChangeBox` likewise `ret nz` twice before any copy (`save.asm:348,360`). A hook at `1c:7b90` therefore never fires on a cancelled save; a hook at the `SaveGameData` entry (`1c:7b91`) would fire before any write and is a **begin** witness, not completion.

**Post-save volatility (FACT):** after the `ret`, `SaveMenu` prints, delays 128 + 10 frames, plays SFX and delays 30 more (`save.asm:158-171`); `TrackPlayTime` keeps incrementing `wPlayTimeFrames` every VBlank while the timer bit is set. So from the first free frame after completion, WRAM `wMainData` differs from `sMainData` by the play-time bytes; a byte-equality check after the fact cannot witness the save (correction 3 stands). **[R2]** The witness must be taken **at** `1c:7b90`; what it can witness there is routine completion and the checksum, not WRAM/SRAM equality (§1).

## 3. Mapping onto the existing hook contract (FACT about the contract; the mapping itself is inference)

- **Site data** (`data/games/gen1_rby/engine_signals.json`, generated by `tools/gen_gen1_engine_signals.py` from `symbols()`/`address()` in `tools/gen_gen1_acquisition_sources.py:48-60`): per kind `{symbol, bank, address, rom_offset, expected_hex (8–9 bytes at address), capture_offset?}`. Precedent for a `ret` site exists: `bag_received` is `AddItemToInventory_.done` with `expected_hex E1D1C1C178EA95CFC9` and `capture_offset 8`, i.e. its PC is the trailing `C9` (`gen_gen1_engine_signals.py:56-60`).
- **A Yellow save-completion site would be** `symbol SavePartyAndDexData, bank 0x1c, address 0x7b56, rom_offset 0x73B56, expected_hex CD9F7E3E01EA0040 (first 8 bytes), capture_offset 58 (0x7b90-0x7b56)`; alternatively `symbol SaveGameData, address 0x7b91, capture_offset 0` for a begin witness. Both are derivable by the existing generator without new mechanisms; Red/Blue addresses differ and are out of this card's scope.
- **Client collector** (`lua/gen1_engine_signals.lua:44-70`): registers `event.on_bus_exec` at `address+capture_offset` on the System Bus, requires `hLoadedROMBank == bank`, `PC == address+capture_offset`, and the site bytes equal `expected_hex` at fire time, after checking the ROM anchor at `rom_offset` once at startup. `point(kind)` for any non-bag kind captures the generic party point (`party_hex`, `trainer_hex`, `player_id_hex`, `map_id`, `battle_flag`, …; `:23-36`). It records no SRAM bytes; whether BizHawk's `CartRAM` domain is readable inside the callback while `rRAMG` is disabled is **unverified**.
- **Server** (`server/gen1_engine_signals.py:25-92`): `validate_signal` accepts a kind only if present in the title's `sites` (`:29`), checks `pc`/`bank` equality and the generic point shape, then branches: `bag_received` (`:36-52`), `battle_faint` (`:73-78`), `poison_faint` (`:79-83`); **[R2] every other kind falls through to the starter checks** (`:84-92`: `map_id == starter_map`, `battle_flag == 0`, `mon_location == 0`, `cur_level == 5`, then `starter_begin`/`starter_end` shape). A `game_saved` signal from any ordinary map would therefore be **refused** (`starter source context differs`), not accepted-unconsumed; and `server/gen1_engine_signal_runtime.py` maps only those existing results. Revision 1's "would validate but have no consumer" is withdrawn: adding a kind requires a server branch in `validate_signal` before a site could even be registered safely.
- The generic point at `1c:7b90` carries the party bytes just copied to `sPartyData`, `map_id` and identity; it does not carry the SRAM checksum, `wSaveFileStatus` or any provenance distinguishing `SaveGameData` from the `cable_club.asm:870` partial path.

## 4. Cheapest future modeled falsifier and the physical observation still required

- **Modeled (no emulator):** a pure data check on the pinned ROM/sym in the generator's existing assertion style (`gen_gen1_engine_signals.py:40-60`): `symbols()["SavePartyAndDexData"] == (0x1c, 0x7b56)`, `symbols()["Bankswitch"] == (0, 0x3e84)`, `symbols()["Predef"] == (0, 0x3eb4)`, `rom[0x73B90] == 0xC9`, `rom[0x73B8A:0x73B90] == EA23B5CDAA7E`, `rom[0x73B91:0x73B9F] == 3E02EA87D0CDE57ACD327BC3567B`, and the source facts `predef SavePartyAndDexData` present at `cable_club.asm:870`. **[R2]** Plus the server-side negative: `validate_signal` with a hypothetical `game_saved` site and a generic point taken on a non-starter map raises `starter source context differs` (`gen1_engine_signals.py:84`), which documents that no new kind can be registered without a server branch.
- **Physical (still required, not claimed):** on a real Yellow cartridge under the free client, (a) one START-menu save fires a `1c:7b90` hook exactly once with `hLoadedROMBank == 0x1c`, `wSaveFileStatus == 2` and CartRAM byte `0x3523 == (255 - sum(sGameData)) & 255`, and separately records whether `wPlayTimeFrames` in WRAM equals the byte just copied into `sMainData` (the equality revision 1 asserted and revision 2 withdraws); (b) a cancelled save (No at either prompt) fires zero times; (c) a Bill's PC box change fires once with an in-bank return address; (d) a completed Cable Club trade fires once via `cable_club.asm:870` with `wSaveFileStatus` unchanged and only party/dex bytes updated — the partial-save case a product consumer must not count as a full save.
