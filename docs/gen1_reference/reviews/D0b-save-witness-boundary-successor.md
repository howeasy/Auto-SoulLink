## 1. The save routine and its completion instruction (FACT, PRET + ROM bytes)

| Symbol | Bank:addr | Flat | Bytes read from the clean ROM | Meaning |
| --- | --- | --- | --- | --- |
| `SaveGameData::` | `1c:7b91` | `0x73B91` | `3E 02 EA 87 D0 CD E5 7A CD 32 7B C3 56 7B` | `ld a,2; ld [wSaveFileStatus=$D087],a; call SaveMainData; call SaveCurrentBoxData; jp SavePartyAndDexData` (`engine/menus/save.asm:274-279`) |
| `SavePartyAndDexData` | `1c:7b56` | `0x73B56` | `CD 9F 7E 3E 01 EA 00 40 …` | third copy: party, dex, Pikachu happiness, then checksum (`save.asm:248-272`) |
| tail of `SavePartyAndDexData` | `1c:7b8a` | `0x73B8A` | `EA 23 B5` `CD AA 7E` `C9` | `ld [sMainDataCheckSum=$B523],a; call DisableSRAM; ret` |
| **completion instruction** | **`1c:7b90`** | **`0x73B90`** | **`C9`** | the `ret` that ends `SavePartyAndDexData`; because `SaveGameData` tail-jumps, this `ret` returns to `SaveGameData`'s **caller** |

At PC `1c:7b90`, before the `ret` executes: all three SRAM copies and the checksum are written, SRAM is disabled again (`DisableSRAM` `1c:7eaa`), `wSaveFileStatus == 2`, and `hLoadedROMBank` (`$FFB8`) is `0x1c`. Nothing after this instruction touches SRAM in the save path. `wPlayTimeFrames` is `00:da44` in Yellow (`pokeyellow.sym`), inside the `wMainData` region the save copies.

## 2. Call and return paths (FACT)

`SaveGameData` has four callers in the pinned tree plus one in the same file:

| Caller | Site | Return address after the `ret` at `1c:7b90` | Path |
| --- | --- | --- | --- |
| `SaveMenu` (`1c:7a67`), START menu SAVE via `predef SaveMenu` (`engine/menus/start_sub_menus.asm:663`, `data/predef_pointers.asm:76`) | `call SaveGameData` at `1c:7a95` (`CD 91 7B`) | `1c:7a98` (`21 D6 7A`, `ld hl, SavingText`) | ordinary player save |
| `ChangeBox::` (`1c:7bea`, `save.asm:342-386`) | `call SaveGameData` after swapping boxes through `CopyBoxToOrFromSRAM` | inside `ChangeBox` | Bill's PC box change = a full save |
| `engine/link/cable_club_npc.asm:70` | `callfar SaveGameData` | cable-club script | link entry quick-save |
| `scripts/HallOfFame.asm:50` | `farcall SaveGameData` | Hall of Fame | end-of-game save |
| `engine/debug/debug_menu.asm:1571` | `callfar SaveGameData` | debug | not reachable in normal play |

**Cancellation (FACT):** `SaveMenu` returns via `ret nz` at `1c:7a7b` (No to "Would you like to save?") and `1c:7a94` (No to "older file will be erased") — both before `call SaveGameData`; no SRAM write, `wSaveFileStatus` unchanged. `ChangeBox` likewise `ret nz` twice before any copy (`save.asm:348,360`). A hook at `1c:7b90` therefore never fires on a cancelled save; a hook at the `SaveGameData` entry (`1c:7b91`) would fire before any write and is a **begin** witness, not completion.

**Post-save volatility (FACT):** after the `ret`, `SaveMenu` prints, delays 128 + 10 frames, plays SFX and delays 30 more (`save.asm:158-171`); `TrackPlayTime` runs every VBlank (`home/vblank.asm:41`, `home/play_time.asm:1-10`, gated by `wStatusFlags6` `BIT_GAME_TIMER_COUNTING`, `wd479` bit 0 and `wPlayTimeMaxed`) and increments `wPlayTimeFrames`. So from the first free frame after completion, WRAM `wMainData` differs from `sMainData` by the play-time bytes; a byte-equality check after the fact cannot witness the save (correction 3 stands). The witness must be taken **at** `1c:7b90`, where `image(WRAM) == SRAM` holds by construction.

## 3. Mapping onto the existing hook contract (FACT about the contract; the mapping itself is inference)

- **Site data** (`data/games/gen1_rby/engine_signals.json`, generated by `tools/gen_gen1_engine_signals.py` from `symbols()`/`address()` in `tools/gen_gen1_acquisition_sources.py:48-60`): per kind `{symbol, bank, address, rom_offset, expected_hex (8–9 bytes at address), capture_offset?}`. Precedent for a `ret` site exists: `bag_received` is `AddItemToInventory_.done` with `expected_hex E1D1C1C178EA95CFC9` and `capture_offset 8`, i.e. its PC is the trailing `C9` (`gen_gen1_engine_signals.py:56-60`).
- **A Yellow save-completion site would be** `symbol SavePartyAndDexData, bank 0x1c, address 0x7b56, rom_offset 0x73B56, expected_hex CD9F7E3E01EA0040 (first 8 bytes), capture_offset 58 (0x7b90-0x7b56)`; alternatively `symbol SaveGameData, address 0x7b91, capture_offset 0` for a begin witness. Both are derivable by the existing generator without new mechanisms; Red/Blue addresses differ and are out of this card's scope.
- **Client collector** (`lua/gen1_engine_signals.lua:44-70`): registers `event.on_bus_exec` at `address+capture_offset` on the System Bus, requires `hLoadedROMBank == bank`, `PC == address+capture_offset`, and the site bytes equal `expected_hex` at fire time, after checking the ROM anchor at `rom_offset` once at startup. `point(kind)` for any non-bag kind captures the generic party point (`party_hex`, `trainer_hex`, `player_id_hex`, `map_id`, `battle_flag`, …; `:23-36`). It records no SRAM bytes; whether BizHawk's `CartRAM` domain is readable inside the callback while `rRAMG` is disabled is **unverified**.
- **Server** (`server/gen1_engine_signals.py:25-60`): `validate_signal` accepts any kind present in the title's `sites`, checks `pc`/`bank` equality and the generic point shape; `server/gen1_engine_signal_runtime.py` maps only `starter_*`, `battle_faint`, `poison_faint`, `bag_received` to semantic events. A new kind would validate but have no consumer until one is added — that consumer is D0b design work, not this card.
- The generic point at `1c:7b90` already carries the exact saved party bytes (`wPartyData` was just copied to `sPartyData`), `map_id` and identity; what it does not carry is the SRAM checksum or `wSaveFileStatus`.

## 4. Cheapest future modeled falsifier and the physical observation still required

- **Modeled (no emulator):** extend the generator's existing site assertions (`gen_gen1_engine_signals.py:40-60` pattern) with a pure data check on the pinned ROM/sym: `symbols()["SavePartyAndDexData"] == (0x1c, 0x7b56)`, `rom[0x73B90] == 0xC9`, `rom[0x73B8A:0x73B90] == EA23B5CDAA7E`, `rom[0x73B91:0x73B9F] == 3E02EA87D0CDE57ACD327BC3567B`, and `validate_signal` accepting `pc 0x7b90 / bank 0x1c` for a site named that way. This fails if the pin, symbol or byte layout ever moves.
- **Physical (still required, not claimed):** on a real Yellow cartridge under the free client, (a) one START-menu save fires the hook exactly once with `hLoadedROMBank == 0x1c`, `wSaveFileStatus == 2` and CartRAM byte `0x3523 == (255 - sum(sGameData)) & 255`; (b) a cancelled save (No at either prompt) fires zero times; (c) a Bill's PC box change and a Cable Club entry each fire once (same PC, different return address on the stack), so a product consumer must classify by caller if it wants "player pressed SAVE" rather than "SRAM was written".

## Unknowns

CartRAM readability inside an exec callback with SRAM disabled (settled by the physical run above); whether `on_bus_exec` at a `ret` fires before the instruction retires in the Gambatte core (the `bag_received` site's live passes make this very likely, not proven for this address).
