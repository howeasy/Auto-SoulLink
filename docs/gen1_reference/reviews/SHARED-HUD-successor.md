Installed BizHawk 2.11 Lua definitions say `gui.clearGraphics` clears all Lua graphics on its surface. [BizHawk API source](https://github.com/TASEmulators/BizHawk/blob/master/src/BizHawk.Client.Common/Api/Classes/GuiApi.cs) implements that as renderer `Clear()`, while `DrawBox` draws/fills under compositing. [BizHawk Lua reference](https://tasvideos.org/Bizhawk/LuaFunctions) describes `clearGraphics` as clearing all Lua graphics and `DrawNew` as surface selection; current source accepts only `emu` and rejects arbitrary names. A transparent box is thus not an erase under normal blending, and a dedicated arbitrary HUD surface is not supported by this API. Narrow production caller search found `gui` drawing in `lua/hud.lua` alone among the Gen1–5 client scripts; those clients call `HUD.render` after their own event logic. This supports whole-surface clear for the current production composition, while separate third-party Lua overlays in the same surface are not modeled or claimed safe.

The shared core now maps optional semantic `kind=link_formed` to compact `Linked!` before viewport fit, retaining legacy untyped `show`, `prompt`, and `present` behavior. The Gen1 service only forwards `kind`; its wire body and receipt are unchanged. The HUD marks its surface dirty only after an actual draw. Each active `render` clears previously painted pixels then redraws transient and persistent state; the first draw on a clean surface needs no clear. Once expiry has cleared the final pixels, empty renders do no GUI work. Empty, never-painted `render` and `clear` work without a `gui` global, matching native-entry model composition and avoiding idle clearing overhead. `present` still draws immediately for a truthful ACK and retains its full render budget so a one-frame notice survives the first clear. Game-over/rebuild state redraws after clears and remains persistent.
