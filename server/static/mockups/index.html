SLink UI mockups

The browser UI is two apps on two ports, built two different ways, with nine destinations between them. These mockups merge the Run Manager and the run dashboard into one workspace and collapse those nine down to three. Same design, built twice — so the framework choice can be judged on evidence rather than on taste.

Track A

Jinja + Alpine + htmx

The stack the project already vendors. No build step, no new dependency, works offline and inside an OBS browser source.

  • The board is the page: one row per pair, both HP bars facing each other, tinted by the weaker half
  • The manager is the rail and the header: new run, start, stop, pin, archive, delete, launchers
  • Fills the viewport at any size; past 1500px the strip sits beside the board
  • Gen 3 ↔ Gen 1 toggle, six body fonts, all nine themes, compact density; Debug on `
 Track B

Vite + Svelte SPA

The same L1 Workspace layout rebuilt as a client app over /api/status, to see what a component framework and a build step would actually buy here.

  • L1 only — the comparison is about the framework, not the layout
  • Built output committed, so it runs without Node installed

Prepared for Gen 1

Gen 1 is the next thoroughly-tested cartridge and it breaks the last shared assumption: with randomized ROM pairs the two players are not playing the same content as each other. Both tracks drive panel visibility off the adapters rather than explaining differences in tooltip prose — a panel a cartridge does not have is absent, not empty. Toggle the cartridge in either mockup and watch columns disappear.

Note that firered and firered_rr differ on two rows. Capability is a property of the cartridge in front of the player, not of the generation — which is why it is read per rom_type.

The body font is an open question

--font-ui is Pixelify Sans today — on-brand, and the hardest thing in the UI to read. Merging the two pages makes that worse rather than better: the run list, both parties, the links table and the event feed now share one viewport, so there is far more small text per screen than either page had alone. The deciding detail is figures: a party table is mostly numbers, and they only read as columns when the digits share a width. Pixelify has no tabular set, so HP values jitter row to row; every candidate below has one.

Track A's mockup switches between them live — Body font in the dashed panel, bottom-left. IBM Plex Sans is the default there and the recommendation. All are vendored, never fetched at runtime.

--font-pixel (Press Start 2P) stays either way: it earns its place on the stream overlays, where text is large, sparse, and read from across a room. The argument is about the dense UI, not about the brand — which lives in the sprites, the palette and the overlays.

The data is real

Every number in these mockups came out of a running server. The fixtures in fixtures/ were captured from /api/status after tools/inject_full_mocks.py, once for Radical Red and once for Red/Blue, and capabilities.json is read straight off the adapters by tools/gen_ui_capabilities.py. Nothing is hand-written, because a hand-written fixture drifts and then the mockup is designing for a payload that does not exist. tests/unit/test_mockup_fixtures.py pins them to _build_status_dict.
